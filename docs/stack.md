## Язык: Python 3.11+

Выбор фактически предопределён транспортным слоем — писать свой реверс протокола
с нуля дороже, чем взять готовый.

| Библиотека | Язык | ★ | Лицензия | Последний пуш | Вывод |
|---|---|---|---|---|---|
| `MaxApiTeam/PyMax` | Python | 231 | MIT | 2026-07-27 | основной кандидат |
| `nsdkinx/vkmax` | Python | 49 | MIT | 2026-03-09 | тишина 4 месяца |
| `rast-games/pyromax` | Python | 27 | MIT | 2026-07-25 | запасной кандидат |
| `mochensky/max-user-api` | Python | 2 | — | 2026-01-24 | автор сам пишет «very early and raw» |
| `MrCatchParkington/go-max-client` | Go | 11 | **AGPL-3.0** | 2026-05-02 | заброшен, лицензия заразна |

Node/TypeScript-библиотек user-уровня не существует вообще — там только Bot API.

Про AGPL отдельно: `go-max-client` под AGPL-3.0 обязал бы открыть исходники
всего сетевого сервиса, построенного поверх него, включая будущую веб-панель.
Даже если проект и так открытый, это навязывает лицензию всему остальному коду.
Плюс библиотека не обновлялась с мая. Go как язык проекта отпадает.

Минимальная версия — 3.11: её требует `pyromax`, `PyMax` довольствуется 3.10.

## Ключевое архитектурное решение: демон + API + тонкие клиенты

CLI **не** делается монолитом. Иначе будущая GUI-оболочка означала бы переписать
ядро.

```
┌─────────────────────────────────────────────┐
│  Ядро (headless-демон, asyncio)             │
│  пул аккаунтов · планировщик · плагины      │
│  адаптер транспорта → PyMax / pyromax       │
└───────────────────┬─────────────────────────┘
                    │ FastAPI: HTTP + WebSocket
                    │ unix-сокет или 127.0.0.1 + токен
        ┌───────────┼───────────┬──────────────┐
        │           │           │              │
      CLI        веб-UI      GUI .exe      сторонние
    (Typer)      (SPA)    (pywebview /    интеграции
                            Tauri)
```

Почему именно так:

- Юзербот обязан держать постоянное соединение — это долгоживущий процесс по
  своей природе, а не команда, отрабатывающая и выходящая. Демон нужен в любом
  случае, даже если бы GUI не планировался.
- Каждый новый интерфейс становится ещё одним клиентом того же API. Ядро не
  трогается.
- FastAPI отдаёт OpenAPI-схему бесплатно — GUI генерирует по ней типизированный
  клиент, а не пишет запросы руками.
- Тот же API одинаково работает локально и на удалённом сервере: GUI на Windows
  может управлять демоном, крутящимся на VPS.

## GUI: поэтапно, без переделки ядра

**Этап 1 — веб-интерфейс.** SPA, которую отдаёт тот же FastAPI. Упаковки нет
вообще, открывается в браузере, одинаково работает локально и на сервере. Этого
достаточно для большинства задач.

**Этап 2 — .exe под Windows.** Два реальных варианта:

| | pywebview | Tauri 2 | Electron |
|---|---|---|---|
| Второй язык и тулчейн | нет, Python | Rust | Node |
| Размер бандла | ~15–30 МБ (PyInstaller) | ~10 МБ | ~150 МБ |
| Движок | WebView2 (есть в Win10/11) | WebView2 | свой Chromium |
| Python-демон | в том же процессе | sidecar-бинарник | sidecar-бинарник |
| Автообновление | руками | из коробки | из коробки |

Рекомендация: **pywebview**, если оболочка остаётся тонкой — не нужен второй
тулчейн, и демон живёт в том же процессе. **Tauri 2**, если понадобится
нормальная установка и автообновление. **Electron** не выбирается ни в одном
сценарии: он тяжелее Tauri в 15 раз и сложнее pywebview, а взамен даёт только
привычность экосистемы Node, которой в проекте всё равно нет.

Общая для обоих вариантов сложность — упаковка Python-демона под Windows
(PyInstaller или Nuitka). Это работа этапа 2, и она не влияет на решения этапа 1.

## Что вынести на ревью

Вопросы, которые должны получить второе мнение до начала кода:

1. Не избыточен ли FastAPI на старте — или на первых порах хватило бы прямого
   вызова ядра из CLI с последующим выносом API.
2. `PyMax` против `pyromax` как основной транспорт: у первого больше покрытие и
   аудитория, у второго удобнее архитектура (Router, FSM, middlewares).
3. Схема хранения сессий: шифрование, права, ротация, поведение при
   компрометации.
4. Антибан-логика: конкретные пороги задержек, адаптивный backoff, реакция на
   ошибки лимитов.
5. Стратегия на случай, если основной транспорт забросят, — насколько тонким
   должен быть адаптер.
