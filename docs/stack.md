## Язык: Python 3.11+

Выбор предопределён транспортным слоем: писать свой реверс протокола дороже, чем
взять готовый.

| Библиотека | Язык | ★ | Лицензия | Последний пуш | Вывод |
|---|---|---|---|---|---|
| `MaxApiTeam/PyMax` | Python | 231 | MIT | 2026-07-27 | основной кандидат |
| `nsdkinx/vkmax` | Python | 49 | MIT | 2026-03-09 | тишина 4 месяца |
| `rast-games/pyromax` | Python | 27 | MIT | 2026-07-25 | второй адаптер |
| `mochensky/max-user-api` | Python | 2 | — | 2026-01-24 | автор сам пишет «very early and raw» |
| `MrCatchParkington/go-max-client` | Go | 11 | AGPL-3.0 | 2026-05-02 | заброшен |

Node/TypeScript-библиотек user-уровня не существует — там только Bot API.

Про `go-max-client`: обязательства AGPL-3.0 зависят от способа связывания,
модификаций и распространения, и веб-панель поверх такой зависимости **не**
становится AGPL автоматически. Но держать AGPL-зависимость в основном процессе —
лишний юридический анализ на каждом релизе, а библиотека вдобавок заброшена.
Go как язык проекта отпадает по второй причине, не по первой.

## Архитектура: демон + API + тонкие клиенты

CLI не делается монолитом — иначе GUI позже означает переписать ядро.

```
┌─────────────────────────────────────────────┐
│  Ядро: application services                 │
│  НЕ зависит от FastAPI, Typer и моделей     │
│  конкретного транспорта                     │
└──┬────────────────────────────────────┬─────┘
   │ входной адаптер                    │ выходной адаптер
   │ FastAPI (тонкий)                   │ транспорт → PyMax
   │ HTTP + WebSocket                   │
   │ 127.0.0.1 + случайный токен        └── MAX
   │
   ├── CLI (Typer, httpx)
   ├── веб-UI (SPA)
   └── GUI .exe (pywebview / Tauri)
```

Ключевое требование ревью: **ядро — обычные сервисы приложения**, FastAPI и
Typer только адаптеры по краям, модели транспортной библиотеки внутрь ядра не
протекают.

Почему демон нужен в любом случае: юзербот держит постоянное соединение, это
долгоживущий процесс по своей природе, а не команда, которая отработала и вышла.

### API — минимальный, но единственный

Поверхность v1: `health/status`, `login`, `accounts`, `send`, `events`,
`shutdown`. WebSocket — только для событий.

Управление идёт **одним путём**: CLI → API. Прямой вызов ядра из CLI допустим
только для bootstrap- и debug-команд. Два равноправных пути быстро разойдутся в
поведении.

Локальный транспорт — `127.0.0.1` со случайным токеном и строгим bind. Unix-сокет
остаётся опцией для Linux: под Windows он сценарий не решает, а Windows здесь
целевая платформа.

Про хранилище отдельно: изначально предполагалось переиспользовать SQLite-базу
`PyMax`. Ревью это отклонило — у транспортного хранилища и прикладной БД разные
схемы, миграции и владельцы, их разделяют физически. Совпадение технологии не
повод объединять файлы.

## Выбор транспорта: не по звёздам, а spike-тестом

`PyMax` — предварительно основной: больше аудитория и покрытие, есть TCP и
WebSocket, есть персистентность сессий. Router/FSM/middleware у `pyromax` — это
удобства уровня фреймворка, и реализовать их лучше над собственным
нормализованным event API, иначе `pyromax` протечёт в ядро.

Окончательное решение — после короткого spike, проверяющего: авторизацию,
reconnect, пагинацию истории, медиа, edit/delete, пропуски событий (event gaps),
два аккаунта одновременно.

Абстрагируется не вся поверхность библиотеки, а только capabilities, реально
нужные v1. У адаптера есть явный список `capabilities`, чтобы отсутствие функции
во втором адаптере не маскировалось молча.

## Антибан, сессии, восстановление

Раздел переписан по итогам ревью: раньше здесь были только намерения.

**Важное предупреждение:** «магических безопасных задержек» для закрытого API не
существует. Гарантированных порогов нет, поэтому проектируется механика, а не
подобранные константы.

Лимиты и защита. Сделано:

- token-bucket плюс случайный jitter, ведро на пару (аккаунт, тип действия);
- разрешение выдаётся по одному: на ключ ведра стоит замок, и «спросить, можно
  ли» и «взять» происходят под ним же, без окна между проверкой и действием;
- обязательное уважение `retry_after`; отказ по лимиту без указания срока
  штрафуется запасным значением, а не остаётся без штрафа вовсе;
- штраф переживает перезапуск демона: он сохраняется в БД и восстанавливается
  при старте;
- долгое ожидание не высиживается в общем цикле отправки — запись возвращается
  в очередь со сроком, чтобы штраф по одному аккаунту не останавливал остальные;
- запрет автоматического повтора потенциально неидемпотентной отправки;
- дедупликация событий и сообщений;
- ручное подтверждение после revoke, подозрения на блокировку и любого исхода,
  который не удалось выяснить. Аккаунт с паролем 2FA адаптер не пускает вовсе.

Не сделано, отложено до живого аккаунта — калибровать эти пороги без данных
сервера значит выдумывать числа:

- отдельные лимиты по чату и адресату (механика ключа это уже позволяет,
  потребитель пока один — отправка текста);
- суточные квоты на аккаунт;
- глобальный cooldown и circuit breaker после риск-сигналов;
- ограничение длины очереди;
- «прогрев» свежего аккаунта пониженными лимитами первых суток.

Состояние и восстановление:

- персистентный sync cursor или checkpoint;
- resync после reconnect **до** возобновления обработчиков;
- явные состояния аккаунта: `connecting`, `syncing`, `ready`, `backoff`,
  `auth_required`, `disabled`.

Сессии:

- права `0600` — необходимый минимум, но недостаточный;
- шифрование at rest, ключ хранится **вне** SQLite: Windows DPAPI или Credential
  Manager, Linux Secret Service, либо явно переданный master key;
- отдельный ключ на аккаунт либо envelope encryption;
- секреты не попадают в логи, трассировки исключений, экспорт и бэкапы;
- атомарная ротация, отзыв старой сессии, отметка времени в аудите;
- API-токен демона ротируется отдельно от сессий MAX.

## Устойчивость к изменениям протокола

- lock-файл в репозитории, проверка лицензий транзитивных зависимостей,
  сохранение MIT-notices;
- фиксация проверенных версий транспорта или верхних границ;
- собственные contract tests поверх записанных обезличенных fixtures;
- аварийный режим при изменении протокола: остановить исходящие действия и не
  уходить в бесконечные повторы.

## GUI: поэтапно

1. **SPA в браузере**, которую отдаёт тот же FastAPI. Упаковки нет.
2. **pywebview** — прототип Windows-оболочки, остаёмся в Python.
3. **Tauri 2** — вероятный вариант для публичного desktop-релиза.
4. **Electron** — только если появится сильная Node-команда или понадобится
   специфичное поведение Chromium.

| | pywebview | Tauri 2 | Electron |
|---|---|---|---|
| Второй тулчейн | нет, Python | Rust | Node |
| Движок | WebView2 | WebView2 | свой Chromium |
| Python-демон | в том же процессе | sidecar | sidecar |
| Автообновление | руками | из коробки | из коробки |

Размеры бандлов из сравнения убраны: до реальной сборки они не критерий —
Python, bootstrapper WebView2, ресурсы и updater существенно меняют цифры.

Самая сложная часть здесь не выбор фреймворка, а **жизненный цикл sidecar**:
запуск, миграции, single-instance, логи, аварийное завершение и совместимость
версий UI и API.
