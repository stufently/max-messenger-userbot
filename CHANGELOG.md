Значимые изменения кода и поведения. Статус работ — в [TASKS.md](TASKS.md).

## 2026-07-30 — гонка за файлом токена и видимые падения CI

### Исправлено

- **Одновременный первый запуск отказывал одному из процессов.** Победитель
  гонки создаёт файл токена флагом `O_EXCL`, но заполняет его следующей
  операцией, и между этими двумя моментами есть окно, в котором файл существует
  пустым. Проигравший крутил три витка без единой паузы, ничего в файле не
  находил и падал с `не удалось создать файл секрета` — то есть отбирал у
  победителя ровно то процессорное время, которого тому не хватало. На машине с
  запасом ядер окно закрывалось раньше, чем кончались витки, поэтому поломка
  жила в коде незамеченной и проявилась на двухъядерном раннере GitHub:
  вероятностно и на случайной версии Python. Теперь проигравший ждёт значение по
  часам, с растущей паузой и общим сроком 5 секунд, а пустой файл, который никто
  не заполняет (остался от упавшего запуска), объясняется словами вместо
  прежнего сообщения «не удалось создать». Сам файл не удаляется: под ним может
  быть чужой каталог данных.
- **Секрет появляется под своим именем целиком.** Ожидание выше — страховка, а
  само окно теперь закрыто: значение пишется во временный файл и публикуется
  одним `os.link`, который атомарен и, в отличие от `os.replace`, не затирает
  чужую работу — занятое имя по-прежнему означает «победил сосед». Пока файла
  под своим именем нет, прочитать обрезанное значение нельзя; заодно запись идёт
  циклом, потому что `os.write` не обязан записать всё за раз (в `write_blob`
  для ключа это учитывалось, для токена — нет). Файловые системы без жёстких
  ссылок (FAT на съёмном диске, часть сетевых томов) сохраняют прежнее
  поведение: там публикуется напрямую, узкое окно лучше отказа запуститься.
  Найдено на ревью Codex.

### Добавлено

- **Текст падения тестов уходит в аннотацию прогона и в его сводку.** Логи
  GitHub Actions отдаёт только по токену с правами администратора репозитория
  (`/actions/jobs/{id}/logs` иначе отвечает «Must have admin rights»), а deploy
  key их не даёт вовсе: публично при красном прогоне видно ровно имя шага и
  «Process completed with exit code 1». Аннотации и сводка, наоборот, доступны
  каждому, кто видит репозиторий, поэтому
  [.github/scripts/report-pytest-failures.sh](.github/scripts/report-pytest-failures.sh)
  кладёт хвост вывода `pytest` туда. Скрипт молчит, если тесты прошли, а упало
  что-то после них: шаг вызывается по `if: failure()` и не знает, что именно
  отказало. Отчёт привязан к коду возврата, а не к слову `FAILED` в выводе:
  иначе аварийные исходы — упавший интерпретатор, «тесты не собрались», код 2–5 —
  остались бы невидимыми, а это ровно то, что труднее всего разбирать. Поводом
  стал прогон, где красные `Тесты (py3.14)` и тесты в образе не воспроизвелись
  локально ни разу из семи попыток; со следующего прогона аннотация назвала тест
  и сообщение, и причина (гонка выше) нашлась за минуты.

## 2026-07-30 — запуск на Linux и публикуемый образ (0.2.0)

### Исправлено

- **Каталог данных по умолчанию был путём из контейнера.** `Settings.data_dir`
  и `ClientSettings.data_dir` по умолчанию равнялись `/data`, поэтому установка
  колесом на обычной машине не запускалась вовсе: демон делает
  `mkdir(parents=True)` и получает отказ доступа в корне. То есть колесо из
  релиза v0.1.0 без `MAXUB_DATA_DIR` было нерабочим — это нашлось при вопросе
  «как запустить на Linux». Теперь путь выбирается по платформе
  ([src/maxub/paths.py](src/maxub/paths.py)): `%LOCALAPPDATA%\maxub` в Windows,
  `~/Library/Application Support/maxub` в macOS, `$XDG_DATA_HOME/maxub` или
  `~/.local/share/maxub` в остальных. Относительный и пустой `XDG_DATA_HOME`
  игнорируются, как требует спецификация: иначе данные оседали бы там, откуда
  запустили демон.
- **Отказ доступа к каталогу объясняется словами.** `ensure_data_dir` называет
  путь и переменную для его смены вместо трассировки `PermissionError`, а файл
  на месте каталога — отдельным сообщением вместо `FileExistsError`. Тип у
  отказа свой (`DataDirError`), потому что обрабатывают его три входа по-разному:
  CLI печатает сообщение и возвращает 1, exe показывает окно (в собранном без
  консоли процессе трассировке выводиться некуда), демон в контейнере падает с
  текстом в журнале. Ловить ради этого любой `RuntimeError` значило бы глотать и
  чужие ошибки — первая версия правки именно этим и грешила, поймано на ревью.
- **Номер версии в коде был один, а мест — три.** `pyproject`,
  `maxub.__version__` и заголовок FastAPI жили порознь, и при выпуске 0.2.0 два
  из трёх остались на 0.1.0. Теперь в коде номер один, API берёт его оттуда, а
  совпадение с `pyproject` сторожит тест: версия установленного пакета читается
  метаданными. Читать метаданные в рантайме нельзя — в собранном exe их нет, если
  не попросить положить явно, и `maxub.exe` падал бы на импорте.
- **Предвыпуск больше не уводит `latest`.** Триггер релиза — `tags: ["v*"]`,
  поэтому `v0.3.0rc1` тоже попадает в публикацию, и без проверки он переставил бы
  и `0.3`, и `latest` на release candidate. Плавающие теги двигает только версия
  вида `X.Y.Z`; сам предвыпуск публикуется под своей точной версией.

### Добавлено

- **Образ публикуется в GHCR** — `ghcr.io/stufently/max-userbot`, теги
  `<версия>`, `<минор>` и `latest`. Собирается штатным `docker build` и
  отправляется штатным `docker push`: ни `docker/*`-actions, ни buildx, ни
  privileged-эмуляции в цепочке поставки нет, пока архитектура одна. Smoke-проверка
  стоит **до** публикации — `docker push` уже выкладывает образ, и проверка после
  него ничего не предотвращает. Права `packages: write` есть только у этой
  работы, `contents: read` указан явно (блок `permissions` обнуляет
  неперечисленное). Метка `org.opencontainers.image.source` нужна для привязки
  пакета к репозиторию.
- **Проверка публикуемого образа на каждом пуше** (не только по тегу): он
  отличается от тестового одним аргументом `EXTRAS`, и этого хватает, чтобы он
  повёл себя иначе. Проверяются подъём демона, healthcheck, выдача токена и
  состав (`pymax` внутри есть, pytest/mypy/ruff — нет), причём на двух схемах
  хранения: named volume и bind-mount с UID хоста.
- **Пользовательский юнит systemd**
  ([packaging/linux/maxub.service](packaging/linux/maxub.service)) с автозапуском
  через `pipx`. `ProtectHome` и `PrivateUsers` в нём намеренно не заданы: первый
  отрезал бы каталог данных, второй — сокет сессионной шины в `/run/user/%U`, и
  ключ шифрования молча уехал бы в файл вместо хранилища ОС. `ReadWritePaths`
  указывает на родителя каталога данных, а не на сам каталог: systemd отказывается
  запускать юнит, если путь из этого списка не существует, — а на чистой установке
  каталог создаёт сам демон при первом запуске. Юнит принят
  `systemd-analyze verify` на systemd 257; на живом сеансе с настоящим Secret
  Service не проверялся — это записано в TASKS.
- **Разделы README**: установка на Linux (`pipx`, venv, где лежат данные,
  systemd), запуск готового образа, выбор между named volume и каталогом на
  хосте, что значат плавающие теги.

### Изменено

- **Образ работает от непривилегированного пользователя** `maxub` (UID 10001),
  ему же принадлежит `/data`. UID задан числом, а не выдан системой: он попадает
  в права файлов на томе, и «какой достался при сборке» означало бы, что после
  пересборки данные оказались чужими.
- **Состав образа задаётся аргументом** `EXTRAS` (по умолчанию `dev,pymax`).
  Публикуемый образ собирается с `EXTRAS=pymax` — без pytest, mypy и ruff.
  Dockerfile остаётся один: два разошлись бы, и пользователь получал бы образ,
  собранный не так, как проверенный.
- **`docker-compose.yml` перешёл на named volume** `maxub-data` и потерял строку
  `user: "1003:1003"`, прошивавшую UID конкретной машины. Прежние данные в
  `./data` не удаляются, но контейнер их больше не видит: вариант с bind-mount
  оставлен в файле закомментированным вместе с `user:`. Кому нужны старые данные
  — вернуть обе строки.
- **Выбор каталога данных перестал жить в обвязке Windows.** `winhost` больше не
  экспортирует `default_data_dir`, а `winlauncher` не подменяет каталог: `Settings`
  берёт нужный сам. Осознанное следствие: у exe и у обычной установки один и тот
  же источник правды.

## 2026-07-30 — CPython 3.14 везде, где версия закреплена

### Добавлено

- **Проверка согласованности версий Python (`versions` в ci.yml).** Версия
  прошита в шести местах, и связать их нечем: `env` одного workflow не виден
  другому, базовый образ закреплён по digest, `setup-python` требует литерал.
  Поводом стал не гипотетический случай: при этом самом обновлении два номера в
  `release.yml` остались на 3.12 и нашлись на ревью, то есть случайно. Теперь
  расхождение падает шагом с обоими значениями в сообщении. Сверяется минор
  (у образа Docker патч выбирает тег, требовать его совпадения было бы
  проверкой, которую пришлось бы отключить при первом обновлении), плюс
  отдельно — что основная версия есть в матрице тестов.

### Изменено

- **Рабочий образ и релизный exe собираются на CPython 3.14.6.** Корневой образ
  — `python:3.14-slim` по новому digest, интерпретатор сборки exe — установщик
  3.14.6 с python.org, `PRIMARY_PYTHON` и обе версии в `release.yml` — 3.14.
  Объявленный контракт не изменился: `requires-python = ">=3.11"` на месте, и
  матрица тестов стала шире, а не сдвинулась — 3.11, 3.12, 3.13, 3.14.
  Проверено, а не предположено: весь закреплённый набор встал на 3.14 готовыми
  колёсами (из исходников собирается только сам `max-userbot`), тесты, `ruff` и
  `mypy` зелёные внутри образа, exe пересобран под Wine и запускается. Целевая
  платформа exe — Windows 11; совместимость со старыми Windows не требуется.
- **Каталог Windows-Python в сборочном образе назван по версии**
  (`C:\Python314`), а путь к интерпретатору собирается из него. Раньше номер
  версии стоял в этом файле четырьмя независимыми значениями вместо двух:
  обновление `PYTHON_VERSION` оставило бы каталог с прежним именем.
- **Подняты закреплённые версии:** `fastapi` 0.141.0 → 0.141.1, `pip`
  26.1.2 → 26.2. У второй обнаружилось следствие, которое стоит знать: в 26.2
  `PIP_CONSTRAINT` больше не доходит до изолированного окружения, в котором
  собирается колесо, — версия hatchling держится там только на
  `PIP_BUILD_CONSTRAINT`. Задавать обе переменные было предусмотрительностью «на
  случай, если pip перестанет распространять первую»; этот случай наступил.
  Закрепление уцелело, потому что обе переменные стоят во всех четырёх местах
  сборки; в файле ограничений записано, чем это замерено.
- **`websockets` сознательно оставлен на 16.1.1**, хотя на PyPI 17.0 и
  `maxapi-python` его формально допускает. Это единственная зависимость, которая
  сама говорит с сервером MAX, а проверить её нечем: тесты подменяют транспорт
  фейком и остаются зелёными на любой версии, то есть мажорное обновление
  сломалось бы не в CI, а у пользователя на живом соединении. Причина записана
  рядом со строкой в файле ограничений — вместе с такой же для `pydantic-core`,
  который не двигается без `pydantic`.
- **Debian в сборочном образе не тронут:** уже trixie на свежем digest, и снимок
  репозитория тот же `20260713T000000Z`.

## 2026-07-30 — среда релизной сборки и запуск собранного exe

### Добавлено

- **Запись о среде сборки уезжает в релиз.** Рядом с exe теперь выкладывается
  `build-env.txt`: версия образа раннера, интерпретатор, версия PyInstaller и
  фактический `pip freeze` (что встало, а не что просили в файле ограничений).
  Спросить у выпущенного файла, чем он собран, раньше было негде: журнал прогона
  живёт 90 дней, а релиз остаётся.
- **Собранный exe проверяется запуском, а не только разбором содержимого.**
  Onefile разворачивает себя во временный каталог и лишь потом поднимает
  интерпретатор, поэтому сломанный загрузчик выглядел как успешная сборка вплоть
  до первого запуска у пользователя. Теперь и CI, и локальная сборка под Wine
  зовут один скрипт (`packaging/windows/smoke_run.sh`), который запускает
  `maxubctl.exe --help` и смотрит не только на код возврата: пустой вывод, вывод
  без кириллицы и вывод с символом замены — это отказ, потому что на кодировке
  эта сборка уже падала. `maxub.exe` не запускается намеренно: он без консоли и
  без аргументов, на раннере это был бы не запуск, а зависший процесс.

### Изменено

- **Поколение ОС сборочного раннера закреплено:** `windows-2025` вместо
  `windows-latest`. Метка `latest` переезжает на следующий Windows Server сама,
  без правки в репозитории, — и релизный exe однажды собрался бы в другой системе
  молча. Полного закрепления это не даёт (образ раннера GitHub обновляет
  примерно раз в неделю, закрепить его состояние можно только на собственном
  раннере) — поэтому незакреплённое и записывается в `build-env.txt`.
- **Подняты закреплённые версии** (предложения Dependabot, проверены целиком, а
  не по одному): базовый образ `python:3.12-slim` и `debian:trixie-slim` по новым
  digest, `fastapi` 0.140.13 → 0.141.0. Дата снимка Debian не изменилась —
  новый digest собран из того же `20260713T000000Z`. Предложение на
  `pydantic-core` 2.47.0 не принято: `pydantic==2.13.4` требует ровно 2.46.4, и
  набор перестал бы ставиться; правило для этого уже стоит в `dependabot.yml`.

## 2026-07-29 — права доступа к API и точка расширения

### Добавлено

- **Токены API с областями доступа.** Раньше право было одно: знающий токен
  распоряжался всеми аккаунтами — читал переписку и писал от имени владельца.
  Теперь токен несёт набор областей (`accounts:read/write`,
  `messages:read/write`, `events:read`, `admin`), и каждый маршрут объявляет, что
  ему нужно; отказ по правам отвечает 403, а не 401, у CLI для него отдельный код
  выхода 8. Токены выпускаются через `maxub tokens add`, отзываются немедленно и
  могут иметь срок. В базе лежит только SHA-256-отпечаток: секрет показывается
  один раз при выпуске и не хранится нигде — копия базы доступа к API не даёт.
  Файловый токен остался корневым, с полным набором прав, поэтому у тех, кто им
  пользуется, ничего не изменилось.
- **Панель работает с правами того токена, которым её открыли.** Сессия браузера
  хранит не слепок прав, а предъявителя, и перепроверяет его на каждом запросе:
  отозванный токен закрывает открытую вкладку сразу, а не через двенадцать часов.
  Одноразовый код входа лаунчера переносит права заказчика — иначе обмен кода на
  сессию был бы способом их повысить. `admin` намеренно не включает остальные
  области, а выдать токену больше, чем есть у выпускающего, нельзя.
- **Контракт точки расширения «событие → обработчик → действие».** Плагины как
  поставка отложены за пределы v1, договор — нет: у аналогов в Telegram он
  дописывался поверх готовой платформы и остался полусломанным. Обработчик
  получает записанное событие из журнала по собственному курсору (значит,
  перезапуск демона работу не теряет), объявляет нужные виды событий и требуемые
  возможности транспорта, а действовать может только через общую очередь
  отправки — те же лимиты, та же идемпотентность, тот же ручной разбор.
  Отправка привязана к аккаунту события: выбрать другой аккаунт обработчик не
  может, а ключ отправки выводится из имени обработчика, номера события и номера
  вызова, поэтому повтор события после падения не создаёт второго сообщения.
  Служебные события самого диспетчера (`handler.*`) обработчикам не раздаются:
  падающий обработчик получал бы собственный отказ, падал на нём и порождал
  следующий — журнал рос бы сам из себя. Ошибка повторяется до трёх раз и только
  потом откладывается с записью `handler.failed` в журнал: вечный повтор
  остановил бы обработчика навсегда, пропуск с первой ошибки превратил бы «хотя
  бы один раз» в «одну попытку». Опечатка в требуемых
  возможностях и повтор имени ломают запуск, а не приводят к тихому простою.

### Изменено

- **Уборка журнала не заходит за курсор обработчика.** Журнал для обработчиков —
  очередь работы, а не «последние события»; подрезка по сроку молча съела бы
  неразобранное. Если разрыв всё же случился (обработчик сняли, журнал
  подрезали, обработчик вернули), при запуске пишется `handler.gap` — пропуск не
  должен выглядеть как «событий не было».

## 2026-07-29 — красный windows-build и предложения Dependabot

### Исправлено

- **Сборка Windows-exe падала на каждом пуше в main.** Причина не в сборке:
  проверка, что библиотека транспорта попала в exe целиком, отрабатывала верно
  (148 модулей `pymax` из 148 в обоих exe) и падала на строке об успехе.
  Windows-Python, чей вывод уходит в пайп, берёт кодировку из ANSI-кодовой
  страницы системы; у раннера GitHub это cp1252, куда кириллица не переводится
  вовсе, — и сообщение по-русски заканчивалось `UnicodeEncodeError` с кодом
  выхода 1. Воспроизведено под Wine на собранных exe: без `PYTHONIOENCODING`
  падает, с `utf-8` проходит. Теперь скрипт проверки сам переводит вывод в UTF-8
  (та же идиома, что и в консольном exe), а job задаёт `PYTHONIOENCODING`, чтобы
  и отказ спеки при отсутствии транспорта был читаемым текстом, а не ошибкой
  кодировки.
- **Предложения Dependabot по `packaging/constraints.txt` приходили
  неустанавливаемыми.** `pydantic` требует свою core-часть точной версией, и
  поднятый в одиночку `pydantic-core` ломал разрешение зависимостей — PR был
  обречён быть вечно красным. Теперь такие обновления приходят одним
  предложением на весь файл (набор и проверяется целиком), а `pydantic-core`
  отдельно не двигается.

### Добавлено

- **Проверка exe выполняется и при локальной сборке под Wine.** Она жила прямо в
  workflow и потому выполнялась ровно в одном месте — на раннере; локальная
  сборка её не делала вовсе, из-за чего расхождение и не всплывало. Скрипт
  вынесен в `packaging/windows/check_bundle.py`, вызывается обоими путями и
  теперь сам покрыт тестами: коды возврата, недостача модулей, архив без PYZ.
- **Сверка базового образа сборочного контейнера со снимком Debian в CI.**
  Digest и дата снимка `snapshot.debian.org` обязаны соответствовать друг другу;
  сам Dockerfile это проверяет, но при сборке, а её в CI нет — релизный exe
  собирается нативно на Windows. Обновление одного digest-а прошло бы все
  проверки зелёным и сломалось бы у того, кто следующим запустит локальную
  сборку.

## 2026-07-29 — сверка с опенсорсными аналогами

Разобраны зрелые юзербот-платформы Telegram, транспортные библиотеки Telethon и
Pyrogram, мосты mautrix и лимитеры Synapse. Ниже — то, что из этого сравнения
пришлось поправить у себя.

### Изменено

- **Долгое ожидание лимита больше не останавливает отправку у всех аккаунтов.**
  Воркер очереди один на весь демон, а `acquire` высиживал штраф сервера прямо в
  цикле: штраф на час по одному аккаунту означал час простоя у остальных, и
  захваченный остаток пачки всё это время висел в `claimed`. Теперь ожидание
  сверх порога (`MAXUB_LIMIT_WAIT_THRESHOLD_SECONDS`, по умолчанию 10 с)
  превращается в отложенную запись: она возвращается в очередь со сроком, а
  воркер идёт к следующей. Попытка при этом не засчитывается — её увеличил
  захват, а в сеть запись не уходила. Telethon и Pyrogram держат похожий порог
  (60 и 10 секунд), но у них клиент обслуживает один аккаунт и ждать никому не
  мешает.
- **Отказ по лимиту без указания срока больше не остаётся без штрафа.** Раньше
  штраф ставился только если сервер прислал `retry_after`; иначе действовал общий
  backoff в несколько секунд, то есть демон возвращался туда, откуда его только
  что прогнали. Запасное значение — `MAXUB_RATE_LIMIT_FALLBACK_SECONDS`, 60 с.
- **Разрешение на действие выдаётся по одному.** Два одновременных вызова на одно
  ведро оба видели свободный токен и оба его списывали. Сегодня потребитель один
  и последовательный, но лимит — защита аккаунта от блокировки, и держаться она
  должна на замке, а не на текущем расположении вызовов.

### Добавлено

- **События о смене состояния аккаунта**: `account.auth_required`,
  `account.backoff`, `account.disabled`. Раньше о потере авторизации и об обрыве
  можно было узнать только опросом `/status` — то есть подписчик живого потока
  пропускал ровно то, ради чего подписывался. Промежуточные `connecting` и
  `syncing` не публикуются: они сменяются парами при каждом переподключении и
  дали бы шум вместо сигнала. Повторная запись того же состояния событием тоже
  не считается — запрос кода ставит аккаунту `auth_required`, а он в нём чаще
  всего и находится.
  Состояние и событие о нём пишутся одной транзакцией, как и при закрытии
  отправки: двумя записями подряд это было бы «состояние сменилось, а никто не
  узнал». Все переходы — включая те, что происходят под надзором за соединением
  и во время входа, — идут через один путь; надзор больше не обращается к
  хранилищу напрямую, а разбор неудачи подключения собран в одном месте, из-за
  чего на старте демона больше не появляются два события об одном переходе.
- **Уборка журнала событий.** Журнал писался на каждое событие и не сжимался, а
  демон рассчитан на месяцы работы. Теперь записи старше
  `MAXUB_EVENTS_RETENTION_DAYS` (90 дней; 0 — не подрезать) удаляются при старте
  и раз в сутки. Очередь отправки не чистится ни при каком значении: дедупликация
  по явному `nonce` бессрочна по контракту, и удаление старой записи тихо
  отменило бы это обещание.
- **Проверка значений лимитов при старте.** Нулевая частота отправки давала
  деление на ноль, отрицательная молча выключала лимит — то есть ровно то, от
  чего лимит защищает. Теперь ошибка в переменной окружения роняет запуск с
  внятным сообщением.
- Тесты ограничителя частоты, шины событий и уборки журнала: ни одного из трёх
  не покрывал ни один тест, при том что в остальных тестах лимитер намеренно
  выключен настройками. Живой поток `WS /ws/events` тоже проверяется теперь —
  отказ без токена, отказ с чужим токеном и доставка события в открытый сокет.
- Дисклеймер в README назван поимённо: конкретные пункты пользовательского
  соглашения (4.3.7, 4.3.10, 4.4, 4.3.4, 4.3.13), подтверждённая пресс-службой
  волна блокировок сторонних клиентов 01.10.2025 и блокировки за однотипный
  текст. Раньше там была общая формулировка «противоречит соглашению».

### Исправлено

- **Ошибка аргументов снова даёт код 2, а не трейсбек.** typer с версии 0.16
  везёт внутри себя собственную копию click (`typer._click`), и её исключения не
  наследуются от классов click, установленного отдельным пакетом: это два
  независимых дерева с одинаковыми именами. Поэтому `except click.ClickException`
  не ловил ничего — забытая обязательная опция, неизвестная команда, непонятное
  значение и вызов группы без подкоманды вылетали трейсбеком с кодом 1, хотя код
  2 объявлен в README частью контракта. Обе копии собираются в
  `cli/errors.py`; сообщение печатается штатным способом click, поэтому к ошибке
  добавились строка `Usage:` и подсказка про `--help`.

## 2026-07-29 — первый реальный транспорт

### Добавлено

- **Адаптер PyMax** (`MAXUB_TRANSPORT=pymax`) — первый транспорт к настоящему
  MAX. Зависимость необязательная: `pip install max-userbot[pymax]`, без неё
  платформа работает на заглушке как раньше. Пакет на PyPI называется
  **`maxapi-python`**; одноимённый `pymax` — это библиотека для термостатов
  eQ-3 и к мессенджеру отношения не имеет.
  **Адаптер не проверен на живом аккаунте.** Проверены исходники библиотеки и
  поведение на подставном модуле; что именно нужно проверить с настоящим
  аккаунтом — перечислено в докстринге модуля.
  Честно объявлено неподдерживаемым: добор пропущенного (PyMax не даёт
  серверной позиции в потоке — события за время простоя теряются) и сверка
  отправки (клиентский идентификатор PyMax генерирует сам, передать свой
  нечем — неоднозначные отправки уходят человеку).
  Неопознанный отказ сервера считается неизвестным исходом, а не «не
  применено»: коды ошибок MAX не документированы, а отказ доказывает лишь то,
  что ответ пришёл.

- Библиотека транспорта попадает в собранные артефакты: образ ставится с
  `.[dev,pymax]`, в Windows-сборку она включается целиком (148 модулей,
  проверяется отдельным шагом CI). Внутри one-file exe совет «поставьте пакет»
  невыполним в принципе, поэтому его там быть не должно. По умолчанию транспорт
  всё равно `stub`: переключение на `pymax` — правка одной строки в
  `docker-compose.yml`, без пересборки.

### Изменено

- `Transport.connect` возвращает обновлённую сессию, если сервер выдал новый
  токен, и ядро сохраняет её сразу. Раньше ротация токена оставалась только в
  памяти процесса: адаптер новый токен получал, сообщить о нём было нечем, и
  следующий запуск просил войти заново сразу после успешного входа.

### Исправлено

- `TransportPermanent` при отправке закрывает запись сразу, а не отправляет её
  на сверку как неизвестный исход. Заведомо неверное сообщение висело в
  `sending` до ручного разбора и прятало за собой действительно неоднозначные.
- Вход сохраняет ту сессию, с которой аккаунт действительно работает. Ротация
  токена на самом первом подключении после SMS или QR затиралась исходной
  сессией: в памяти оставался новый токен, в базе — старый.
- Новый ключ шифрования больше не создаётся и тогда, когда хранилище ОС
  доступно, но пусто. Пустое хранилище — это не обязательно первый запуск: ключ
  мог потеряться вместе с профилем или связкой, а база с сессиями осталась.
  Проверка стояла только на пути отказа хранилища.

## 2026-07-29 — ключ в хранилище ОС, отказ от записи, снимок сборки

### Добавлено

- **Ключ шифрования сессий умеет жить в хранилище ОС**: Windows DPAPI (через
  `ctypes`, без новых зависимостей) и Linux Secret Service (через необязательный
  `keyring`). Порядок источников — `MAXUB_SECRET_KEY`, хранилище ОС, файл
  `secret.key`: каждый следующий шире по охвату и слабее по защите. Режимом
  `MAXUB_SECRET_KEY_STORE` можно потребовать хранилище явно (`os`) или отключить
  его (`file`). Отсутствие хранилища — штатный случай: в Docker всё работает как
  раньше, файлом.
  Существующий `secret.key` копируется в хранилище, а не переносится: молчаливое
  удаление отрезало бы откат и доступ к сессиям, если хранилище пропадёт.
  Удаление — отдельное решение (`MAXUB_SECRET_KEY_DROP_FILE`), и только после
  того, как ключ прочитан из хранилища обратно.
  Новый ключ поверх живой базы теперь не создаётся вовсе: это тихая потеря всех
  сессий, поэтому демон честно отказывается стартовать.
- **Отказ от записи в очереди**: `maxub discard --id N --reason ...` — «разобрал
  и решил не отправлять». Отдельное терминальное состояние `discarded`, а не
  `failed`: «не получилось» и «решили не отправлять» — разные вещи и для
  человека, и для статистики. Причина обязательна и хранится отдельно от
  `error`, который объясняет, почему запись вообще попала к человеку.
- Системная часть сборочного образа закреплена снимком репозитория Debian. Дата
  снимка берётся из того, что записал о себе базовый образ, поэтому согласована
  с его digest по построению; сборка падает сразу, если digest подняли, а дату
  забыли.

## 2026-07-29 — дистрибутив под Windows и CI

### Добавлено

- **Автономная сборка под Windows**: `maxub.exe` запускается двойным щелчком,
  поднимает демон на свободном петлевом порту и открывает веб-панель в
  браузере. Ни установки Python, ни командной строки. Рядом — консольный
  `maxubctl.exe` для скриптов и агентов: он сам находит адрес работающего
  демона. Каталог данных — `%LOCALAPPDATA%\maxub`.
- Защита от второго экземпляра: именованный мьютекс плюс `runtime.json` с
  адресом демона. Две копии на одной базе — это две очереди отправки и два
  соединения одного аккаунта; повторный запуск открывает панель, а не поднимает
  второго демона.
- Сборка exe из Docker через Wine (`packaging/windows/`) — чтобы собирать с
  Linux-машины, — и нативная сборка на раннере Windows для релиза. Спека
  PyInstaller одна и та же: расхождение сборок обнаружилось бы у пользователя.
- **CI** (`.github/workflows/ci.yml`): ruff, проверка форматирования, mypy,
  тесты на Python 3.11–3.13, отдельный прогон внутри Docker-образа и проверка
  того, что статика веб-панели действительно попадает в wheel.
- **Автосборка релиза** по тегу `v*`: wheel, sdist и `maxub.exe` собираются и
  прикладываются к релизу. Тег сверяется с версией пакета, иначе релиз уехал бы
  с чужим номером.

- **Закреплена Python-часть сборки**: базовые образы взяты по digest, а точные
  версии пакетов — в `packaging/constraints.txt`, подключённом к сборке образа,
  дистрибутивов и exe. Нижние границы в `pyproject.toml` при этом остались: это
  контракт для тех, кто ставит пакет с PyPI, а закреплённый набор нужен только
  сборке. Проверки в CI намеренно идут на плавающих версиях — иначе о
  несовместимости с новым релизом зависимости мы узнавали бы из отчётов об
  ошибках, а не из красного прогона.
  Полной воспроизводимости это ещё не даёт: `apt-get` в сборочном образе берёт
  текущие версии Wine и системных пакетов из изменяемого репозитория. Для
  строгой гарантии нужен снимок репозитория Debian или заранее собранный
  сборочный образ, закреплённый по digest.
- **Ручной разбор очереди**: `maxub outbox` показывает застрявшие записи
  (отказавшие и «в полёте») с ошибкой, числом попыток и временем, а
  `maxub retry --id N` повторяет конкретную. В API — `GET /outbox` и
  `POST /outbox/{id}/retry`.
  Повтор разрешён только из `failed`: перехватывать запись у работающего
  воркера нельзя. Перед отправкой всегда выполняется сверка с сервером — она
  ничего не отправляет и может только уменьшить вред; если сервер подтвердил
  доставку, запись закрывается как отправленная и повтора не происходит. Исход
  сверки и риск дубля возвращаются явно: человек повторяет сообщение, которое
  могло дойти.
- **Одноразовый код входа в панель** вместо копирования токена в буфер обмена.
  Лаунчер получает код по `POST /web/handoff` (маршрут закрыт тем же
  bearer-токеном), открывает браузер на `/web/enter?code=…`, и тот меняет код на
  обычную сессию панели с перенаправлением на `/web`. Код живёт две минуты и
  гаснет при первом обращении, поэтому адрес в истории браузера бесполезен.
  Копирование токена в буфер убрано совсем: буфер переживает вставку, попадает в
  историю Windows и в облачную синхронизацию, а токен бессрочен.
  Вход по токену в форму остался — в Docker лаунчера нет.

### Исправлено

- Демон не запускался в Windows вовсе: `chmod` по открытому SQLite-файлу `-shm`
  падает с «файл занят другим процессом». Там права всё равно определяет ACL
  профиля, поэтому в Windows выставление битов пропускается.
- `os.O_NOFOLLOW` в Windows не существует, и создание файла токена падало с
  `AttributeError` ещё до старта. Флаг берётся, если он есть.
- Два одновременно стартующих процесса на пустом каталоге дрались за файл
  токена: проигравший получал `FileExistsError` из `O_EXCL` и падал. Теперь
  проигравший читает значение победителя. Гонка воспроизводилась в 191 попытке
  из 200.
- Адрес демона из `runtime.json` проверяется до использования: только `http` на
  петлевой адрес, без учётных данных, пути и запроса. Иначе подменённый файл
  увёл бы bearer-токен клиента на чужой сервер.
- Защита от второго экземпляра переехала с именованного мьютекса на блокировку
  файла в каталоге данных. Мьютекс в области `Local\` разделён по сеансам
  Windows: тот же пользователь, зашедший ещё и по RDP, поднял бы вторую копию
  на той же базе. Замок берётся до создания секретов, а неудача трактуется как
  «занято»: допустить две копии хуже, чем не запуститься.
- Имя тега в публикации релиза передаётся через переменную окружения, а не
  подставляется в текст команды.

## 2026-07-29 — веб-панель и гарантии доставки

### Добавлено

  DNS), `Cache-Control: no-store` и CSP `default-src 'none'`. Существующий API
  cookie не принимает — он по-прежнему только bearer.
- Версионированные миграции БД через `PRAGMA user_version`: обновление больше не
  ломает существующую базу. Шаги применяются под блокировкой с перечиткой
  версии, поэтому два одновременно стартующих демона не мешают друг другу.
- Состояние очереди `claimed` — «захвачено, но транспорт этого ещё не видел».
- Отдельный ответ `429` на превышение числа незавершённых запросов входа.

### Изменено

- **Контракт транспорта.** `fetch_updates` и `events()` отдают `Update` с
  позицией сервера: раньше живой поток сохранял в качестве курсора
  идентификатор сообщения, а добор — курсор транспорта, и у реального адаптера
  эти значения несовместимы.
- **Сверка отправки стала трёхзначной**: `find_by_client_token` заменён на
  `reconcile_send` с исходами «найдено», «доказано, что не дошло» и «выяснить не
  удалось». Повтор разрешён только во втором случае — раньше «не нашли» и «не
  смогли выяснить» были неразличимы, и второе приводило к дублю у получателя.
- Подписка на живой поток открывается до добора пропущенного: между концом
  добора и началом подписки было окно, в котором событие терялось.
- Счётчик попыток переподключения обнуляется только после соединения,
  прожившего 30 секунд. Раньше он сбрасывался после каждой попытки, и задержка
  всегда оставалась минимальной — экспоненты не было.
- Незавершённый добор больше не выдаёт себя за догнанный: неподвижный курсор
  при непустой порции считается неисправностью транспорта, а упор в предел
  страниц публикует `account.backfill_incomplete`.
- Отметка об отправке и событие о ней пишутся одной транзакцией.
- Запросы входа ограничены сроком жизни, одним живым запросом на аккаунт и
  потолком на процесс; обращения к одному запросу сериализованы.
- Новая сессия сохраняется только после успешного подключения.

### Исправлено по ревью Codex

- Пачка, захваченная воркером, помечалась отправляемой целиком, хотя отправка
  идёт по одной. После падения на первой записи остальные считались
  неоднозначными и терялись; теперь `sending` ставится вплотную к сетевому
  вызову, а захваченное возвращается в очередь без всякой сверки.
- Неизвестный исход в штатной работе списывался в `failed` даже там, где
  транспорт умеет сверять: доставленное сообщение показывалось неудачным, а
  ручной повтор давал дубль.
- Аккаунт, не поднявшийся при старте демона, оставался в `backoff` без надзора и
  не подключался до перезапуска процесса.
- `secrets.compare_digest` сравнивает байты: заголовок `Authorization` с
  не-ASCII символами валил запрос в 500 вместо отказа. То же в обработчике
  WebSocket — там соединение падало с ошибкой вместо закрытия кодом 4401.
- Запись в БД сериализована общим замком. Хранилище работает через одно
  соединение, а между операторами составной операции есть `await` — чужая
  корутина успевала зафиксировать наполовину сделанную работу, и «одна
  транзакция» ею не была. Замок реентерабельный по задаче: вложенная запись
  считается частью внешней транзакции, а не встаёт в дедлок.
- Аккаунт больше не объявляется готовым с мёртвой подпиской. Живой поток мог
  умереть во время добора — например, сразу после последней пустой страницы, —
  и аккаунт переходил в `ready`, хотя слушать сервер уже некому. Теперь
  подписка подтверждается явным handshake, а смерть потока во время добора
  считается неуспешным подключением и отдаётся надзорному циклу.
- Проверка `Host` в панели отключалась целиком при `0.0.0.0` — то есть ровно
  в штатном для Docker режиме проброса порта. Адрес привязки больше не
  считается доверенным именем: петля разрешена всегда, остальное — явным
  списком `MAXUB_WEB_ALLOWED_HOSTS`.
- Веб-маршруты входа отвечали 404 на превышение лимита запросов входа, тогда
  как основной API отдаёт 429.

## 2026-07-29 — готовность к реальному транспорту

### Добавлено

- **Вход по QR-коду** как второй способ авторизации: `login qr` показывает код
  символами прямо в терминале и ждёт подтверждения, а `login qr-start` и
  `login qr-poll` дают те же шаги неблокирующими вызовами для скриптов.
  В API — `/login/qr/start` и `/login/qr/poll`.
- Команда `capabilities` и маршрут `/accounts/{id}/capabilities`: клиент
  спрашивает у транспорта, что тот умеет, вместо догадок.
- Добор пропущенных событий по курсору при подключении и переподключении.
- Надзорный цикл на каждый аккаунт: переподключение с нарастающей паузой и
  случайным разбросом.
- Сверка отправки, исход которой остался неизвестным: если транспорт умеет
  искать сообщение по клиентскому токену, исход выясняется у сервера, и только
  при отсутствии такой возможности запись отдаётся человеку.
- Отложенные повторы: срок следующей попытки хранится в БД, поэтому переживает
  перезапуск. Штрафы от сервера по `retry_after` тоже сохраняются.
- Шифрование сессий в базе, ключ вне базы — из `MAXUB_SECRET_KEY` либо из файла
  с правами 0600. Есть перешифровка всех сессий новым ключом.
- Файл `LICENSE` — MIT.

### Изменено

- Ядро разделено на три части: состав операций (`service`), очередь отправки
  (`sender`) и соединения (`sync`). Зависимости описаны узкими протоколами в
  `ports`, а не конкретными классами.
- Ключ идемпотентности собирается с указанием длин полей: раньше значения со
  служебным символом внутри могли дать один ключ для разных сообщений.
- `send_text` в контракте транспорта принимает клиентский токен — без него
  выяснить судьбу сообщения после обрыва невозможно.

## 2026-07-29 — каркас v1

### Добавлено

- Ядро (`src/maxub/core/`): доменные модели с состояниями аккаунта, прикладная
  БД на SQLite отдельно от сессионного хранилища транспорта, очередь отправки с
  ключом идемпотентности, журнал событий с дедупликацией, курсор синхронизации.
- Ограничение частоты: token bucket на пару «аккаунт + действие», случайный
  джиттер, учёт `retry_after` от сервера.
- Контракт транспорта (`src/maxub/transport/`): `Protocol` с явным списком
  возможностей, таксономия ошибок, заглушечная реализация для проверки всего
  пути без реального аккаунта MAX.
- Локальный API (`src/maxub/api/`): `health`, `status`, `accounts`, `login`,
  `send`, `history`, `events`, `shutdown` и поток событий по WebSocket.
  Аутентификация bearer-токеном со сравнением, постоянным по времени.
- Два CLI (`src/maxub/cli/`): `maxub` с таблицами и `maxubctl` с JSON и
  стабильными кодами выхода для скриптов и агентов.
- Docker: сборка, `compose` с запуском от UID 1003, healthcheck.
- 34 теста: ядро, API, контракт CLI, восстановление после сбоя.

### Исправлено по ревью Codex

- Сообщения, застрявшие в состоянии отправки после падения процесса, больше не
  висят вечно: при старте они помечаются неуспешными с явной причиной. Вслепую
  не переотправляются — сообщение могло уйти получателю.
- Захват очереди стал атомарным (`UPDATE ... RETURNING`): раньше два воркера
  могли прочитать одни и те же записи и отправить сообщение дважды.
- Постановка в очередь и добавление аккаунта разрешают гонку уникальным
  индексом вместо проверки до вставки.
- Запущен поток входящих событий: раньше `Transport.events()` не вызывался
  вообще, и входящие сообщения не попадали в журнал.
- Дедупликация без явного nonce ограничена окном в 60 секунд. Раньше повторно
  отправить тот же текст в тот же чат было невозможно навсегда.
- Каталог данных переведён на права 0700, БД вместе с WAL и SHM — на 0600.
  В базе лежат сессии аккаунтов, а SQLite создавал файлы по umask.
- Токен API создаётся атомарно с правами 0600 вместо «записать, потом chmod».
- Токен WebSocket принимается заголовком, а не query-параметром, и сравнивается
  постоянным по времени сравнением.
- Демон в контейнере слушает петлю вместо `0.0.0.0`: иначе он был доступен
  любому соседнему контейнеру в общей сети Docker.
- Добавлены лимит попыток отправки, ограниченная очередь подписчика событий и
  верхние границы длины текста, метки и размера страницы.
- Цикл отправки переживает необработанную ошибку вместо остановки навсегда.
- Аккаунты поднимаются при рестарте не только из готового состояния, но и из
  `connecting` и `backoff`; остановленные вручную не поднимаются.
- Каталог `data/` добавлен в `.gitignore` — токен и БД с сессиями не должны
  попадать в репозиторий.
