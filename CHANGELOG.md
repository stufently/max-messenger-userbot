# Changelog

Значимые изменения кода и поведения. Статус работ — в [TASKS.md](TASKS.md).

## 2026-07-29 — дистрибутив под Windows и CI

### Добавлено

- **Автономная сборка под Windows**: `maxub.exe` запускается двойным щелчком,
  поднимает демон на свободном петлевом порту и открывает веб-панель в
  браузере. Ни установки Python, ни командной строки. Рядом — консольный
  `maxubctl.exe` для скриптов и агентов: он сам находит адрес работающего
  демона. Каталог данных — `%LOCALAPPDATA%\maxub`.
- Защита от второго экземпляра: именованный мьютекс плюс `runtime.json` с
  адресом демона. Две копии на одной базе — это две очереди отправки и два
  соединения одного аккаунта; повторный запуск открывает панель, а не поднимает
  второго демона.
- Сборка exe из Docker через Wine (`packaging/windows/`) — чтобы собирать с
  Linux-машины, — и нативная сборка на раннере Windows для релиза. Спека
  PyInstaller одна и та же: расхождение сборок обнаружилось бы у пользователя.
- **CI** (`.github/workflows/ci.yml`): ruff, проверка форматирования, mypy,
  тесты на Python 3.11–3.13, отдельный прогон внутри Docker-образа и проверка
  того, что статика веб-панели действительно попадает в wheel.
- **Автосборка релиза** по тегу `v*`: wheel, sdist и `maxub.exe` собираются и
  прикладываются к релизу. Тег сверяется с версией пакета, иначе релиз уехал бы
  с чужим номером.

- **Закреплена Python-часть сборки**: базовые образы взяты по digest, а точные
  версии пакетов — в `packaging/constraints.txt`, подключённом к сборке образа,
  дистрибутивов и exe. Нижние границы в `pyproject.toml` при этом остались: это
  контракт для тех, кто ставит пакет с PyPI, а закреплённый набор нужен только
  сборке. Проверки в CI намеренно идут на плавающих версиях — иначе о
  несовместимости с новым релизом зависимости мы узнавали бы из отчётов об
  ошибках, а не из красного прогона.
  Полной воспроизводимости это ещё не даёт: `apt-get` в сборочном образе берёт
  текущие версии Wine и системных пакетов из изменяемого репозитория. Для
  строгой гарантии нужен снимок репозитория Debian или заранее собранный
  сборочный образ, закреплённый по digest.
- **Ручной разбор очереди**: `maxub outbox` показывает застрявшие записи
  (отказавшие и «в полёте») с ошибкой, числом попыток и временем, а
  `maxub retry --id N` повторяет конкретную. В API — `GET /outbox` и
  `POST /outbox/{id}/retry`.
  Повтор разрешён только из `failed`: перехватывать запись у работающего
  воркера нельзя. Перед отправкой всегда выполняется сверка с сервером — она
  ничего не отправляет и может только уменьшить вред; если сервер подтвердил
  доставку, запись закрывается как отправленная и повтора не происходит. Исход
  сверки и риск дубля возвращаются явно: человек повторяет сообщение, которое
  могло дойти.
- **Одноразовый код входа в панель** вместо копирования токена в буфер обмена.
  Лаунчер получает код по `POST /web/handoff` (маршрут закрыт тем же
  bearer-токеном), открывает браузер на `/web/enter?code=…`, и тот меняет код на
  обычную сессию панели с перенаправлением на `/web`. Код живёт две минуты и
  гаснет при первом обращении, поэтому адрес в истории браузера бесполезен.
  Копирование токена в буфер убрано совсем: буфер переживает вставку, попадает в
  историю Windows и в облачную синхронизацию, а токен бессрочен.
  Вход по токену в форму остался — в Docker лаунчера нет.

### Исправлено

- Демон не запускался в Windows вовсе: `chmod` по открытому SQLite-файлу `-shm`
  падает с «файл занят другим процессом». Там права всё равно определяет ACL
  профиля, поэтому в Windows выставление битов пропускается.
- `os.O_NOFOLLOW` в Windows не существует, и создание файла токена падало с
  `AttributeError` ещё до старта. Флаг берётся, если он есть.
- Два одновременно стартующих процесса на пустом каталоге дрались за файл
  токена: проигравший получал `FileExistsError` из `O_EXCL` и падал. Теперь
  проигравший читает значение победителя. Гонка воспроизводилась в 191 попытке
  из 200.
- Адрес демона из `runtime.json` проверяется до использования: только `http` на
  петлевой адрес, без учётных данных, пути и запроса. Иначе подменённый файл
  увёл бы bearer-токен клиента на чужой сервер.
- Защита от второго экземпляра переехала с именованного мьютекса на блокировку
  файла в каталоге данных. Мьютекс в области `Local\` разделён по сеансам
  Windows: тот же пользователь, зашедший ещё и по RDP, поднял бы вторую копию
  на той же базе. Замок берётся до создания секретов, а неудача трактуется как
  «занято»: допустить две копии хуже, чем не запуститься.
- Имя тега в публикации релиза передаётся через переменную окружения, а не
  подставляется в текст команды.

## 2026-07-29 — веб-панель и гарантии доставки

### Добавлено

- **Веб-панель `/web`** для аккаунтов: список с состояниями и последней ошибкой
  и автообновлением, добавление аккаунта, вход по коду из SMS и по QR-коду,
  отключение аккаунта. QR рисуется на сервере и вставляется как `data:`-URI —
  страница работает без интернета и без единого стороннего скрипта.
  Отключается целиком через `MAXUB_WEB_UI=false`.
- Вход в панель: токен демона обменивается на сессионную cookie
  (`HttpOnly`, `SameSite=Strict`, TTL 12 ч) с CSRF-меткой, которая живёт только
  в памяти вкладки. Добавлены проверка петлевого `Host` (против перепривязки
  DNS), `Cache-Control: no-store` и CSP `default-src 'none'`. Существующий API
  cookie не принимает — он по-прежнему только bearer.
- Версионированные миграции БД через `PRAGMA user_version`: обновление больше не
  ломает существующую базу. Шаги применяются под блокировкой с перечиткой
  версии, поэтому два одновременно стартующих демона не мешают друг другу.
- Состояние очереди `claimed` — «захвачено, но транспорт этого ещё не видел».
- Отдельный ответ `429` на превышение числа незавершённых запросов входа.

### Изменено

- **Контракт транспорта.** `fetch_updates` и `events()` отдают `Update` с
  позицией сервера: раньше живой поток сохранял в качестве курсора
  идентификатор сообщения, а добор — курсор транспорта, и у реального адаптера
  эти значения несовместимы.
- **Сверка отправки стала трёхзначной**: `find_by_client_token` заменён на
  `reconcile_send` с исходами «найдено», «доказано, что не дошло» и «выяснить не
  удалось». Повтор разрешён только во втором случае — раньше «не нашли» и «не
  смогли выяснить» были неразличимы, и второе приводило к дублю у получателя.
- Подписка на живой поток открывается до добора пропущенного: между концом
  добора и началом подписки было окно, в котором событие терялось.
- Счётчик попыток переподключения обнуляется только после соединения,
  прожившего 30 секунд. Раньше он сбрасывался после каждой попытки, и задержка
  всегда оставалась минимальной — экспоненты не было.
- Незавершённый добор больше не выдаёт себя за догнанный: неподвижный курсор
  при непустой порции считается неисправностью транспорта, а упор в предел
  страниц публикует `account.backfill_incomplete`.
- Отметка об отправке и событие о ней пишутся одной транзакцией.
- Запросы входа ограничены сроком жизни, одним живым запросом на аккаунт и
  потолком на процесс; обращения к одному запросу сериализованы.
- Новая сессия сохраняется только после успешного подключения.

### Исправлено по ревью Codex

- Пачка, захваченная воркером, помечалась отправляемой целиком, хотя отправка
  идёт по одной. После падения на первой записи остальные считались
  неоднозначными и терялись; теперь `sending` ставится вплотную к сетевому
  вызову, а захваченное возвращается в очередь без всякой сверки.
- Неизвестный исход в штатной работе списывался в `failed` даже там, где
  транспорт умеет сверять: доставленное сообщение показывалось неудачным, а
  ручной повтор давал дубль.
- Аккаунт, не поднявшийся при старте демона, оставался в `backoff` без надзора и
  не подключался до перезапуска процесса.
- `secrets.compare_digest` сравнивает байты: заголовок `Authorization` с
  не-ASCII символами валил запрос в 500 вместо отказа. То же в обработчике
  WebSocket — там соединение падало с ошибкой вместо закрытия кодом 4401.
- Запись в БД сериализована общим замком. Хранилище работает через одно
  соединение, а между операторами составной операции есть `await` — чужая
  корутина успевала зафиксировать наполовину сделанную работу, и «одна
  транзакция» ею не была. Замок реентерабельный по задаче: вложенная запись
  считается частью внешней транзакции, а не встаёт в дедлок.
- Аккаунт больше не объявляется готовым с мёртвой подпиской. Живой поток мог
  умереть во время добора — например, сразу после последней пустой страницы, —
  и аккаунт переходил в `ready`, хотя слушать сервер уже некому. Теперь
  подписка подтверждается явным handshake, а смерть потока во время добора
  считается неуспешным подключением и отдаётся надзорному циклу.
- Проверка `Host` в панели отключалась целиком при `0.0.0.0` — то есть ровно
  в штатном для Docker режиме проброса порта. Адрес привязки больше не
  считается доверенным именем: петля разрешена всегда, остальное — явным
  списком `MAXUB_WEB_ALLOWED_HOSTS`.
- Веб-маршруты входа отвечали 404 на превышение лимита запросов входа, тогда
  как основной API отдаёт 429.

## 2026-07-29 — готовность к реальному транспорту

### Добавлено

- **Вход по QR-коду** как второй способ авторизации: `login qr` показывает код
  символами прямо в терминале и ждёт подтверждения, а `login qr-start` и
  `login qr-poll` дают те же шаги неблокирующими вызовами для скриптов.
  В API — `/login/qr/start` и `/login/qr/poll`.
- Команда `capabilities` и маршрут `/accounts/{id}/capabilities`: клиент
  спрашивает у транспорта, что тот умеет, вместо догадок.
- Добор пропущенных событий по курсору при подключении и переподключении.
- Надзорный цикл на каждый аккаунт: переподключение с нарастающей паузой и
  случайным разбросом.
- Сверка отправки, исход которой остался неизвестным: если транспорт умеет
  искать сообщение по клиентскому токену, исход выясняется у сервера, и только
  при отсутствии такой возможности запись отдаётся человеку.
- Отложенные повторы: срок следующей попытки хранится в БД, поэтому переживает
  перезапуск. Штрафы от сервера по `retry_after` тоже сохраняются.
- Шифрование сессий в базе, ключ вне базы — из `MAXUB_SECRET_KEY` либо из файла
  с правами 0600. Есть перешифровка всех сессий новым ключом.
- Файл `LICENSE` — MIT.

### Изменено

- Ядро разделено на три части: состав операций (`service`), очередь отправки
  (`sender`) и соединения (`sync`). Зависимости описаны узкими протоколами в
  `ports`, а не конкретными классами.
- Ключ идемпотентности собирается с указанием длин полей: раньше значения со
  служебным символом внутри могли дать один ключ для разных сообщений.
- `send_text` в контракте транспорта принимает клиентский токен — без него
  выяснить судьбу сообщения после обрыва невозможно.

## 2026-07-29 — каркас v1

### Добавлено

- Ядро (`src/maxub/core/`): доменные модели с состояниями аккаунта, прикладная
  БД на SQLite отдельно от сессионного хранилища транспорта, очередь отправки с
  ключом идемпотентности, журнал событий с дедупликацией, курсор синхронизации.
- Ограничение частоты: token bucket на пару «аккаунт + действие», случайный
  джиттер, учёт `retry_after` от сервера.
- Контракт транспорта (`src/maxub/transport/`): `Protocol` с явным списком
  возможностей, таксономия ошибок, заглушечная реализация для проверки всего
  пути без реального аккаунта MAX.
- Локальный API (`src/maxub/api/`): `health`, `status`, `accounts`, `login`,
  `send`, `history`, `events`, `shutdown` и поток событий по WebSocket.
  Аутентификация bearer-токеном со сравнением, постоянным по времени.
- Два CLI (`src/maxub/cli/`): `maxub` с таблицами и `maxubctl` с JSON и
  стабильными кодами выхода для скриптов и агентов.
- Docker: сборка, `compose` с запуском от UID 1003, healthcheck.
- 34 теста: ядро, API, контракт CLI, восстановление после сбоя.

### Исправлено по ревью Codex

- Сообщения, застрявшие в состоянии отправки после падения процесса, больше не
  висят вечно: при старте они помечаются неуспешными с явной причиной. Вслепую
  не переотправляются — сообщение могло уйти получателю.
- Захват очереди стал атомарным (`UPDATE ... RETURNING`): раньше два воркера
  могли прочитать одни и те же записи и отправить сообщение дважды.
- Постановка в очередь и добавление аккаунта разрешают гонку уникальным
  индексом вместо проверки до вставки.
- Запущен поток входящих событий: раньше `Transport.events()` не вызывался
  вообще, и входящие сообщения не попадали в журнал.
- Дедупликация без явного nonce ограничена окном в 60 секунд. Раньше повторно
  отправить тот же текст в тот же чат было невозможно навсегда.
- Каталог данных переведён на права 0700, БД вместе с WAL и SHM — на 0600.
  В базе лежат сессии аккаунтов, а SQLite создавал файлы по umask.
- Токен API создаётся атомарно с правами 0600 вместо «записать, потом chmod».
- Токен WebSocket принимается заголовком, а не query-параметром, и сравнивается
  постоянным по времени сравнением.
- Демон в контейнере слушает петлю вместо `0.0.0.0`: иначе он был доступен
  любому соседнему контейнеру в общей сети Docker.
- Добавлены лимит попыток отправки, ограниченная очередь подписчика событий и
  верхние границы длины текста, метки и размера страницы.
- Цикл отправки переживает необработанную ошибку вместо остановки навсегда.
- Аккаунты поднимаются при рестарте не только из готового состояния, но и из
  `connecting` и `backoff`; остановленные вручную не поднимаются.
- Каталог `data/` добавлен в `.gitignore` — токен и БД с сессиями не должны
  попадать в репозиторий.

## 2026-07-29

### Добавлено

- `docs/features.md` — каталог сценариев автоматизации MAX: что делают
  существующие проекты, потолок возможностей транспортного слоя, переносимые
  плагины из Telegram.
- `docs/stack.md` — стек: Python 3.11+, архитектура «демон + локальный API +
  тонкие клиенты», этапы построения GUI.

### Изменено

- `docs/stack.md` доработан по ревью Codex: ядро развязано с FastAPI и Typer,
  локальный транспорт API переведён с unix-сокета на `127.0.0.1` с токеном ради
  Windows, прикладная БД отделена от сессионной БД транспорта, выбор `PyMax`
  переведён в статус «подтвердить spike-тестом», разделы про антибан, сессии и
  восстановление состояния расписаны механикой вместо намерений, формулировка
  про AGPL смягчена как юридически неточная.

- Первоначальная документация проекта: README с описанием, сравнением
  «бот против юзербота», FAQ и дисклеймером.
- `docs/research.md` — ландшафт автоматизации MAX, аналоги в Telegram, риски.
- `docs/seo.md` — нейминг, description, topics, правила для текстов.
- `CLAUDE.md` — архитектурные принципы и правила работы над проектом.
- `TASKS.md` — рабочий журнал.
