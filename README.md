# MAX Userbot — автоматизация пользовательских аккаунтов в мессенджере МАКС (max.ru)

[![ci](https://github.com/stufently/max-messenger-userbot/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/stufently/max-messenger-userbot/actions/workflows/ci.yml)
[![windows-build](https://github.com/stufently/max-messenger-userbot/actions/workflows/windows-build.yml/badge.svg?branch=main)](https://github.com/stufently/max-messenger-userbot/actions/workflows/windows-build.yml)
[![Python 3.11+](https://img.shields.io/badge/python-3.11%2B-blue)](https://www.python.org/downloads/)
[![License: MIT](https://img.shields.io/badge/license-MIT-green)](LICENSE)

**MAX Userbot — это открытая платформа автоматизации пользовательских аккаунтов
российского мессенджера MAX (Макс, max.ru), написанная на Python.** Юзербот
работает от имени обычного аккаунта через внутренний API мессенджера, а не через
официальный Bot API: он видит те же чаты, что и вы, и не требует регистрации
бота. Проект даёт мультиаккаунт, очередь отправки с защитой от дублей,
веб-панель управления, CLI и сборку под Windows одним файлом.

> **Статус на 30 июля 2026: ранняя разработка.** Каркас платформы работает и
> покрыт автотестами, но транспорт пока заглушечный — подключения к настоящему
> MAX ещё нет. Подключение реальной библиотеки транспорта — следующий шаг, см.
> [TASKS.md](TASKS.md).

## Что такое юзербот для мессенджера MAX

Юзербот — это программа, которая подключается к мессенджеру под вашим обычным
пользовательским аккаунтом и выполняет действия за вас: отвечает на сообщения,
пересылает их между чатами, выгружает историю, работает по расписанию. В отличие
от чат-бота, юзербот не является отдельным участником переписки — с точки зрения
собеседника действия совершаете вы сами.

Термин пришёл из экосистемы Telegram, где юзерботы существуют больше десяти лет
(Ultroid, Userge, catuserbot). В MAX эта ветка только формируется.

## Чем юзербот отличается от бота в MAX

| | Бот (Bot API) | Юзербот (этот проект) |
|---|---|---|
| От чьего имени работает | отдельный аккаунт-бот | ваш обычный аккаунт |
| API | официальный `platform-api.max.ru` | внутренний API мессенджера |
| Кто может опубликовать | только верифицированные юрлица, ИП и самозанятые — резиденты РФ | ограничений на публикацию нет |
| Видит переписку в обычных чатах | нет | да |
| Нужно приглашать в чат | да | нет |
| Поддержка со стороны MAX | официальная | отсутствует |
| Риск для аккаунта | отсутствует | блокировка за нарушение правил |

Коротко: бот — это отдельный участник чата, которого нужно куда-то пригласить.
Юзербот работает как вы сами и видит ровно то, что видите вы.

## Чем это отличается от библиотек PyMax, pyromax и vkmax

На 29 июля 2026 года под MAX существует шесть библиотек транспортного уровня —
`PyMax`, `vkmax`, `pyromax`, `MaxAPI`, `max-user-api`,
`max-messenger-mobile-api-unofficial` — и ни одной платформы поверх них. Полный
разбор с цифрами — в [docs/research.md](docs/research.md).

| | Библиотека транспорта | MAX Userbot |
|---|---|---|
| Что даёт | вызовы внутреннего API | готовую платформу поверх любого транспорта |
| Мультиаккаунт | пишете сами | встроен |
| Очередь отправки, повторы, дедупликация | пишете сами | встроены |
| Ограничение частоты действий | пишете сами | включено по умолчанию |
| Восстановление после обрыва связи | пишете сами | добор пропущенного по курсору |
| Хранение сессий | обычно файл рядом | шифрование, ключ вне базы |
| Интерфейс | код | веб-панель, CLI, HTTP API |
| При смене протокола MAX | переписываете свой код | меняется только адаптер транспорта |

Проект сознательно не конкурирует с этими библиотеками: любая из них может стать
его транспортом. Ориентир по продукту — «Ultroid для MAX».

## Что уже работает

- **Два способа входа** — по номеру телефона с кодом и по QR-коду, который
  сканируется приложением MAX. QR рисуется прямо в терминале.
- **Веб-панель** — добавление и авторизация аккаунтов мышью, без командной
  строки: список аккаунтов с состояниями, вход по коду и по QR.
- **Демон** с пулом аккаунтов и очередью отправки: дедупликация по ключу
  идемпотентности, ограничение частоты, отложенные повторы, явные состояния
  аккаунта. Штраф сервера по одному аккаунту не останавливает отправку у
  остальных и переживает перезапуск демона.
- **Живой поток событий** — входящие сообщения, отправки, отказ от записи, а
  также состояния аккаунта: потеря авторизации, обрыв связи, выключение.
- **Восстановление после сбоя** — добор пропущенных событий по курсору,
  переподключение с нарастающей паузой, сверка отправки, исход которой остался
  неизвестным.
- **Шифрование сессий** — в базе они лежат зашифрованными, ключ хранится вне
  базы.
- **Локальный API** — HTTP и WebSocket, только на петлевом интерфейсе, с
  обязательным токеном и правами по областям доступа.
- **Два CLI** — `maxub` для человека и `maxubctl` для скриптов и агентов.
- **Сборка под Windows** — один `maxub.exe` без установки Python.
- **Docker** — сборка, запуск и тесты.

По умолчанию транспорт заглушечный (`stub`): весь путь от команды до записи в
журнал проверяется без реального аккаунта MAX. Адаптер к настоящему MAX есть, но
**на живом аккаунте ещё не проверен** — см. ниже.

## Подключение к настоящему MAX

В Docker и в сборке под Windows библиотека уже внутри — достаточно переключить
транспорт:

```bash
MAXUB_TRANSPORT=pymax   # в docker-compose.yml или в окружении
```

При установке пакетом библиотеку нужно попросить явно — дополнением `[pymax]` к
имени:

```bash
pip install "max-userbot[pymax] @ <ссылка на колесо из релиза>"
```

Ссылка, а не короткое имя: на PyPI проекта пока нет, он появится там отдельным
шагом. Готовые команды со ссылкой — ниже, в разделе «Linux: установка».

Адаптер написан поверх библиотеки [PyMax](https://github.com/MaxApiTeam/PyMax).
На PyPI она называется **`maxapi-python`** — одноимённый пакет `pymax` это
библиотека для термостатов eQ-3 и к мессенджеру отношения не имеет.

Что адаптер сознательно не умеет — и почему:

| Возможность | Состояние | Причина |
|---|---|---|
| Отправка и история | есть | — |
| Вход по телефону и по QR | есть | — |
| Добор пропущенного за простой | нет | PyMax не даёт серверной позиции в потоке событий, подставить идентификатор сообщения нельзя — это другое пространство значений |
| Сверка неоднозначной отправки | нет | клиентский идентификатор PyMax генерирует сам, передать свой нечем — такие записи уходят человеку |
| Аккаунт с паролем 2FA | нет | вход прерывается понятной ошибкой, а не виснет в ожидании ввода: в демоне пароль спросить не у кого |
| Правка и удаление сообщений, вложения | нет | в контракте транспорта таких методов пока нет |

Проверить, что умеет транспорт конкретного аккаунта, можно прямо из CLI:
`maxubctl capabilities --account-id 1`.

## Что планируется

- **Пересылка (форвардинг)** — правила «из чата А в чат Б» с фильтрами и
  преобразованием текста, живая синхронизация.
- **Планировщик** — отложенные и повторяющиеся отправки.
- **Плагины** — модульное ядро, свои сценарии без правки самого ядра.
- **Мост MAX ↔ Telegram** — первый внешний плагин после стабилизации ядра.

Каталог сценариев автоматизации — в [docs/features.md](docs/features.md).

## Windows: один файл

Скачайте `maxub.exe` из [релизов](https://github.com/stufently/max-messenger-userbot/releases)
и запустите двойным щелчком. Установка Python не нужна, командная строка тоже:
демон поднимается сам на свободном порту, а браузер открывается на панели
управления.

Данные лежат в `%LOCALAPPDATA%\maxub`: база с сессиями, токен, `launcher.log`.
Второй запуск не поднимает вторую копию, а открывает панель уже работающей — две
копии на одной базе означали бы две очереди отправки и два соединения одного
аккаунта.

Рядом лежит `maxubctl.exe` — консольный клиент для скриптов и агентов, он сам
находит адрес работающего демона. Обычному пользователю он не нужен. Третий файл,
`build-env.txt`, — запись о том, чем собран этот exe: версия образа раннера,
интерпретатор и фактические версии зависимостей. Нужен он ровно в одном случае —
когда сборка ведёт себя иначе, чем предыдущая, и надо понять, чем они
отличаются.

Файл не подписан, поэтому при первом запуске Windows покажет предупреждение
SmartScreen. Собрать самому:

```bash
bash packaging/windows/build.sh   # результат в dist/windows/
```

## Linux: установка

Отдельного бинарника под Linux нет, и это осознанно: колесо из релиза —
`py3-none-any`, оно и есть линуксовый артефакт, а рядом лежит готовый образ.
Собранный же одним файлом ELF был бы привязан к версии glibc сборочной машины и
не запустился бы на системах старше неё — цена такой хрупкости выше пользы там,
где есть `pipx` и Docker.

Проще всего — `pipx`: программа встаёт в свой изолированный venv, а команды
появляются в `~/.local/bin`. Номер версии в ссылках ниже — из релиза, который был
последним на момент правки этого текста; актуальный список всегда на странице
[релизов](https://github.com/stufently/max-messenger-userbot/releases/latest).

```bash
pipx install "max-userbot[pymax] @ https://github.com/stufently/max-messenger-userbot/releases/download/v0.2.0/max_userbot-0.2.0-py3-none-any.whl"
maxub daemon
```

Без `pipx` — обычный venv:

```bash
python3 -m venv ~/.local/share/maxub-venv
~/.local/share/maxub-venv/bin/pip install "max-userbot[pymax] @ https://github.com/stufently/max-messenger-userbot/releases/download/v0.2.0/max_userbot-0.2.0-py3-none-any.whl"
~/.local/share/maxub-venv/bin/maxub daemon
```

Данные — токен API, БД с сессиями и ключ — лежат в `$XDG_DATA_HOME/maxub`, а если
переменная не задана, в `~/.local/share/maxub`. Каталог создаётся с правами
`0700`. Сменить его — `MAXUB_DATA_DIR`.

Чтобы ключ шифрования сессий жил не в файле рядом с базой, а в хранилище ОС
(GNOME Keyring, KWallet), нужен дополнительный набор: установите
`max-userbot[pymax,keyring]`. Подробности — в «Хранение секретов».

Автозапуск — пользовательским юнитом systemd, готовый лежит в
[packaging/linux/maxub.service](packaging/linux/maxub.service):

```bash
mkdir -p ~/.local/share/maxub ~/.config/systemd/user
cp packaging/linux/maxub.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now maxub
loginctl enable-linger "$USER"   # работать и без входа в сеанс
```

Юнит именно пользовательский: демон держит сессии личного аккаунта, под root ему
делать нечего, а хранилище ключей ОС живёт в сеансе пользователя и системному
юниту недоступно.

## Docker: готовый образ

```bash
docker run -d --name maxub \
  -v maxub-data:/data \
  -e MAXUB_TRANSPORT=stub \
  ghcr.io/stufently/max-userbot:0.2.0

docker exec maxub maxub accounts list
```

Образ работает от непривилегированного пользователя (UID 10001) и хранит данные
в `/data`. Порт наружу не публикуется — демон управляет живыми аккаунтами, и
доступ к нему только через `docker exec`.

Архитектура — только `amd64`, и другой не планируется. На Raspberry Pi и в
облаках на Graviton или Ampere этот образ не запустится; там ставьте колесо
через `pipx` (см. раздел выше). Само колесо `py3-none-any`, а у зависимостей с
бинарной частью на PyPI есть готовые колёса `aarch64` — на 64-битной системе
ничего компилировать не придётся. На 32-битной Raspberry Pi OS (`armv7l`) это
уже не так: часть колёс под неё не выкладывают, и установка с `[pymax]`
упрётся в сборку из исходников.

Про том. `maxub-data` — named volume, права на него Docker выставляет сам. Если
данные нужны в своём каталоге на хосте, добавляется `--user`, иначе владелец
каталога и пользователь внутри контейнера не совпадут:

```bash
mkdir -p ~/.local/share/maxub          # иначе каталог создаст Docker, и от root
docker run -d --name maxub \
  --user "$(id -u):$(id -g)" \
  -v "$HOME/.local/share/maxub:/data" \
  ghcr.io/stufently/max-userbot:0.2.0
```

Теги: точная версия (`0.2.0`) публикуется один раз и больше не переставляется,
минорная (`0.2`) получает исправления внутри себя, `latest` — просто последнее.
Держите живые аккаунты на точной версии: плавающий тег однажды приедет с
изменённым поведением в неподходящий момент. Предвыпуски (`0.3.0rc1`) выкладываются
только под своей точной версией и `latest` за собой не уводят.

Веб-панель наружу не выставляется. Чтобы открыть её со своей машины, пробросьте
порт на петлю хоста (`-p 127.0.0.1:8765:8765`), задайте `MAXUB_HOST=0.0.0.0` —
иначе проброс упрётся в петлю внутри контейнера — и, если хост не локальный,
ходите туннелем: `ssh -L 8765:127.0.0.1:8765 <хост>`. Цена решения описана в
`docker-compose.yml`: демон становится виден и соседям по сети Docker, защищает
его только токен.

## Быстрый старт в Docker из исходников

Сборка своего образа вместо готового — тот же Dockerfile, что и в релизе:

```bash
docker compose up -d --build
docker compose exec userbot maxub accounts list
```

Данные лежат в томе `maxub-data`, а не в каталоге репозитория: права на том не
зависят от того, какой у вас UID на этой машине. Удаляется он вместе с данными —
`docker compose down -v`. Кому нужен именно каталог рядом с кодом, тот
раскомментирует в `docker-compose.yml` bind-mount и строку `user:` — иначе
владелец каталога и пользователь внутри контейнера не совпадут.

**Если вы обновляетесь с версии, где данные лежали в `./data`.** До 0.2.0
compose монтировал каталог репозитория, и `git pull && docker compose up -d`
поднимет демон уже на пустом томе: новый `secret.key`, новая база, аккаунты
придётся заводить заново. Прежние файлы никуда не делись — они в `./data`, но
контейнер их больше не видит, а сессии в базе зашифрованы ключом из `secret.key`
рядом. Переносите каталог целиком: разъехавшиеся база и ключ — это нечитаемые
сессии. Есть два пути:

- остаться на каталоге: раскомментировать в `docker-compose.yml` bind-mount
  `./data:/data` и строку `user:`, запускать через
  `UID=$(id -u) GID=$(id -g) docker compose up -d`;
- переехать в том, скопировав каталог как есть:

```bash
docker compose down
docker compose run --rm --no-deps -u 0 \
  -v "$PWD/data:/from:ro" --entrypoint sh userbot \
  -c 'cp -a /from/. /data/ && chown -R 10001:10001 /data'
docker compose up -d
```

Том здесь не назван по имени намеренно: `compose run` подключает тот же самый,
что и `compose up`, а собственное имя тома зависит от имени проекта — каталога,
`COMPOSE_PROJECT_NAME` или ключа `-p`, — и написанное в README имя увело бы
данные в чужой том на любой машине, где проект назван иначе. `-u 0` нужен только
на время копирования: владельцем файлов сразу же становится пользователь образа.

И не делайте `docker compose down -v`, пока не убедились, где лежат рабочие
данные: ключ шифрования удаляется вместе с томом, а без него сессии не
восстановить.

Полный путь от добавления аккаунта до отправки сообщения:

```bash
docker compose exec userbot maxub accounts add --phone "+79990000000" --label рабочий
docker compose exec userbot maxub login start --account-id 1
docker compose exec userbot maxub login complete --challenge-id <id> --code <код>
docker compose exec userbot maxub send --account-id 1 --chat-id <чат> --text "привет"
docker compose exec userbot maxub history --account-id 1 --chat-id <чат>
```

У заглушечного транспорта код подтверждения всегда `00000`.

## Вход по QR-коду

Второй способ авторизации: код сканируется приложением MAX на телефоне, SMS не
нужен. Одна команда показывает код и ждёт подтверждения:

```bash
docker compose exec userbot maxub login qr --account-id 1
```

QR рисуется символами, поэтому работает и по ssh, и в выводе
`docker compose exec` — картинка не требуется.

Для скриптов те же шаги разделены на два неблокирующих вызова:

```bash
docker compose exec userbot maxubctl login qr-start --account-id 1
docker compose exec userbot maxubctl login qr-poll --challenge-id <id>
```

`qr-poll` возвращает `pending`, `confirmed` или `expired` и не ждёт.

## Веб-панель

Если возиться с командами не хочется, аккаунты добавляются и авторизуются через
страницу. Она показывает список аккаунтов с их состоянием и последней ошибкой,
умеет запросить код на телефон, показать QR для сканирования и отключить
аккаунт.

Панель отдаёт тот же демон, отдельный сервер поднимать не нужно. По умолчанию
порт наружу не публикуется — как открыть доступ, написано в комментарии внутри
[docker-compose.yml](docker-compose.yml). После этого:

1. Откройте `http://127.0.0.1:8765/web`.
2. Введите токен демона — его выдаст
   `docker compose exec userbot cat /data/api_token`.

В сборке под Windows вводить ничего не нужно: лаунчер сам получает одноразовый
код входа и открывает панель уже готовой к работе. Код действует две минуты и
гаснет при первом переходе, поэтому сам токен в браузер не попадает вовсе.

Токен вводится один раз и в браузере не хранится: он обменивается на сессионную
cookie (`HttpOnly`, `SameSite=Strict`, 12 часов), а каждый изменяющий запрос
дополнительно подписывается CSRF-меткой, которая живёт только в памяти вкладки.
Страница не тянет ни одного внешнего файла и работает без интернета. Панель
управляет только аккаунтами: отправки сообщений и просмотра истории в ней нет,
это осталось в CLI.

Панель отключается целиком, если она не нужна:

```bash
MAXUB_WEB_UI=false
```

## `maxubctl` — режим для скриптов и агентов

`maxubctl` — та же программа, что и `maxub`, но заточенная под неинтерактивный
вызов: JSON по умолчанию, никаких запросов ввода, токен подхватывается из
каталога данных. Агент заходит в работающий контейнер и действует сам:

```bash
docker compose exec userbot maxubctl status
docker compose exec userbot maxubctl events --after-id 12
docker compose exec userbot maxubctl capabilities --account-id 1
```

Если отправка застряла — например, связь оборвалась и выяснить исход не удалось,
— запись остаётся человеку, а не переотправляется вслепую:

```bash
docker compose exec userbot maxub outbox          # что зависло и почему
docker compose exec userbot maxub retry --id 42   # повторить конкретную запись
docker compose exec userbot maxub discard --id 42 --reason "уже написал вручную"
```

Перед повтором демон сам спрашивает сервер, дошло ли сообщение. Если дошло —
запись закрывается как отправленная, и повтора не будет. Если выяснить не
удалось, повтор произойдёт, но получатель может увидеть сообщение дважды — это
осознанное решение человека, и команда о нём предупреждает.

Коды выхода стабильны — разбирать текст ошибки не нужно:

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | прочая ошибка |
| 2 | ошибка аргументов |
| 3 | демон недоступен |
| 4 | неверный или отсутствующий токен |
| 5 | конфликт состояния (дубль аккаунта, аккаунт не готов) |
| 6 | возможность не поддерживается транспортом |
| 7 | объект не найден |
| 8 | токен опознан, но прав не хватает |

Курсор `--after-id` в `events` позволяет читать поток без повторов — агент
хранит последний увиденный `id` и продолжает с него.

## Токены и права доступа

Токен из каталога данных — корневой: он даёт все права и предъявляется владельцем.
Скрипту, помощнику или обработчику событий выдаётся свой токен ровно с теми
правами, которые ему нужны:

```bash
docker compose exec userbot maxub tokens add --label "монитор" \
    --scope accounts:read --scope events:read --scope messages:read
docker compose exec userbot maxub tokens list
docker compose exec userbot maxub tokens revoke --id 3
```

| Область | Что открывает |
|---|---|
| `accounts:read` | список аккаунтов, состояние демона, возможности транспорта |
| `accounts:write` | добавить аккаунт, войти в него, остановить |
| `messages:read` | история чата и очередь отправки |
| `messages:write` | отправка, повтор и отказ от записи очереди |
| `events:read` | журнал событий и живой поток (вместе с `messages:read`) |
| `admin` | выпуск и отзыв токенов, остановка демона |

Значение токена показывается один раз при выпуске: демон хранит только его
отпечаток и повторить выдачу не может. Отзыв действует немедленно, в том числе
для уже открытой веб-панели — панель работает с правами того токена, которым её
открыли.

`events:read` требует и `messages:read`: в журнале лежат тексты входящих
сообщений, и право следить за состоянием не должно давать доступ к переписке.

## Как устроен проект

Архитектура — демон с локальным API и тонкие клиенты поверх него. Веб-панель и
оба CLI — это клиенты одного и того же API, поэтому новый интерфейс не требует
переписывать ядро.

```
клиенты          maxub · maxubctl · веб-панель
                          │  HTTP + WebSocket, токен
демон            FastAPI ─┴─ ядро: аккаунты, очередь, события, лимиты
                          │  Protocol с явным списком возможностей
транспорт        адаптер конкретной библиотеки (PyMax, pyromax, …)
```

Три решения, определяющие остальное:

1. **Транспорт изолирован за интерфейсом.** Внутренний API MAX меняется без
   предупреждения — за последний год сменились и домен, и схема авторизации.
   Конкретная библиотека остаётся деталью реализации за абстракцией.
2. **Лимиты включены по умолчанию, а не опцией.** Консервативные задержки между
   действиями и адаптивный backoff работают изначально.
3. **Сессии — секреты.** Шифрование в базе, ключ вне базы, права `0600`.

Точка расширения зафиксирована до v1: журнал событий с курсором — это и есть
очередь работы обработчика, а действовать он может только через общую очередь
отправки, то есть под теми же лимитами, что и человек. Загрузка сторонних
плагинов отложена, договор «событие → обработчик → действие» — нет: у аналогов
в Telegram плагины дописывались поверх готовой платформы и потому остались
полусломанными.

Подробнее — в [docs/stack.md](docs/stack.md) и [CLAUDE.md](CLAUDE.md).

## Требования

- Что-то одно из трёх: Python 3.11 или новее (Linux, macOS — `pipx`), Docker
  (любая система) или готовый `maxub.exe` под Windows 11.
- Аккаунт MAX с доступом к номеру телефона (для входа по коду) или к приложению
  на телефоне (для входа по QR).
- Для Docker: возможность запускать контейнеры от своего пользователя.
- Для хранилища ключей ОС на Linux: сеанс с GNOME Keyring или KWallet и набор
  `max-userbot[keyring]`. Без него ключ шифрования просто останется в файле.

## Хранение секретов

В каталоге данных лежат две чувствительные вещи: токен доступа к API и база с
сессиями аккаунтов. Права — `0700` на каталог и `0600` на файлы.

Сессии в базе зашифрованы. Ключ ищется в трёх местах по порядку:

1. переменная `MAXUB_SECRET_KEY` — ключ вообще не касается диска;
2. хранилище ОС — Windows DPAPI или Linux Secret Service (нужен
   `pip install max-userbot[keyring]`). Прочитать ключ сможет только тот же
   пользователь на той же машине;
3. файл `secret.key` рядом с базой — работает везде, включая контейнер.

Каждый следующий источник шире по охвату и слабее по защите. Хранилища ОС может
не быть — это не ошибка: в Docker всё работает как раньше, файлом. Потребовать
хранилище явно или отключить его — `MAXUB_SECRET_KEY_STORE=os|file|auto`.

При переходе на хранилище существующий `secret.key` копируется, а не удаляется:
иначе пропадёт и откат, и доступ к сессиям, если хранилище потеряется. Удалить
файл — отдельное решение (`MAXUB_SECRET_KEY_DROP_FILE=true`).

Каталог `data/` внесён в `.gitignore` — секреты не должны попадать в
репозиторий.

В Windows права на файлы задаются не битами доступа, а ACL: биты там ничего не
решают, и код их не трогает. Защиту даёт сам `%LOCALAPPDATA%` — доступ к нему
есть у владельца, SYSTEM и администраторов. Если задать свой каталог через
`MAXUB_DATA_DIR`, его права придётся обеспечить самостоятельно: положив данные в
общедоступное место, вы отдадите туда и токен, и базу с сессиями.

## Лимиты и их настройка

Значения по умолчанию консервативные, но «гарантированно безопасных» порогов для
закрытого API не существует — MAX своих лимитов не публикует. Механика такая:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `MAXUB_SEND_RATE_PER_MINUTE` | 12 | сколько сообщений в минуту разрешено аккаунту |
| `MAXUB_SEND_BURST` | 3 | запас действий подряд после простоя |
| `MAXUB_SEND_JITTER_SECONDS` | 1.5 | случайная добавка к каждой паузе |
| `MAXUB_LIMIT_WAIT_THRESHOLD_SECONDS` | 10 | дольше этого ожидание не высиживается: запись возвращается в очередь со сроком |
| `MAXUB_RATE_LIMIT_FALLBACK_SECONDS` | 60 | штраф, когда сервер отказал по лимиту, но срока не назвал |
| `MAXUB_EVENTS_RETENTION_DAYS` | 90 | сколько дней хранить журнал событий; 0 — не подрезать |

Порог ожидания существует потому, что очередь разбирает один воркер на все
аккаунты. Без него получасовой штраф по одному аккаунту означал бы получасовой
простой у всех остальных.

Отказ сервера по лимиту всегда сильнее собственного расчёта: `retry_after`
сохраняется в базу и действует после перезапуска демона.

## Разработка

```bash
docker build -t max-userbot:dev .
docker run --rm -v "$PWD:/app" -w /app --user "$(id -u):$(id -g)" \
    -e HOME=/tmp -e PYTHONPATH=/app/src max-userbot:dev \
    sh -c "python -m pytest -q && ruff check . && mypy src/maxub"
```

`PYTHONPATH=/app/src` обязателен: иначе Python возьмёт копию пакета, вшитую в
образ, а не примонтированный исходник.

Проверки те же, что в CI: `ruff check`, `ruff format --check`, `mypy` в строгом
режиме и полный набор автотестов на Python 3.11, 3.12, 3.13 и 3.14.

## Частые вопросы

**Что такое юзербот для MAX?**
Юзербот для MAX — это программа, которая подключается к мессенджеру MAX под
вашим обычным аккаунтом и выполняет действия за вас: отвечает, пересылает,
собирает сообщения, работает по расписанию.

**Чем юзербот отличается от чат-бота MAX?**
Бот требует верификации юрлица и работает как отдельный участник чата. Юзербот
действует от вашего имени, не требует регистрации в MAX и видит обычные чаты.
Подробности — в таблице выше.

**Можно ли вести несколько аккаунтов MAX одновременно?**
Да. Мультиаккаунт заложен с первого дня: один процесс обслуживает пул аккаунтов
с изолированным состоянием у каждого.

**Как получить сессию MAX?**
Через авторизацию по номеру телефона с кодом подтверждения или по QR-коду, как в
обычном клиенте. Сессия сохраняется локально в зашифрованном виде и
переиспользуется при следующих запусках.

**Нужен ли для юзербота официальный MAX Bot API?**
Нет. Bot API покрывает только ботов и не даёт доступа к пользовательскому
аккаунту. Юзербот работает через внутренний API мессенджера.

**Существуют ли готовые библиотеки для MAX на Python?**
Да, на 29 июля 2026 года их шесть: `PyMax`, `vkmax`, `pyromax`, `MaxAPI`,
`max-user-api`, `max-messenger-mobile-api-unofficial`. Все они — транспортного
уровня. Обзор с цифрами — в [docs/research.md](docs/research.md).

**Можно ли запустить юзербот MAX на Windows без Python?**
Да. Скачайте `maxub.exe` из релизов и запустите двойным щелчком — он поднимет
демон и откроет панель управления в браузере.

**Забанят ли аккаунт за юзербот в MAX?**
Такой риск есть: использование юзербота противоречит пользовательскому
соглашению MAX. Проект включает консервативные лимиты по умолчанию и не
содержит функций массовых рассылок, но гарантий не даёт никто.

**Можно ли делать рассылки через юзербот MAX?**
Нет. Массовые рассылки, сбор чужих данных и добавление пользователей в чаты в
проект не добавляются — это прямой путь к блокировке и, в зависимости от
сценария, к нарушению законодательства о персональных данных.

**Работает ли проект с настоящим MAX прямо сейчас?**
Транспорт к настоящему MAX написан и включается одной строкой
(`MAXUB_TRANSPORT=pymax`), библиотека уже внутри образа и внутри `maxub.exe`. Но
на живом аккаунте он **не проверен**: адаптер написан по исходникам библиотеки, а
не по поведению сервера. По умолчанию стоит заглушка — чтобы `docker compose up`
в незнакомом окружении ничего не трогал.

**Забанят ли за сторонний клиент, если ничего не рассылать?**
Риск есть и он подтверждён публично: 1 октября 2025 года MAX сообщил о
блокировке доступа через сторонние приложения, блокировали по номеру телефона.
Известны и блокировки за один и тот же текст, отправленный разным людям вручную —
то есть детектор смотрит не только на объём. Подробности и пункты соглашения — в
[дисклеймере](#дисклеймер).

## Термины и синонимы

MAX, Макс, макс мессенджер, max.ru, MAX Messenger — один и тот же российский
мессенджер. Юзербот, userbot, user-bot, юзер-бот — программа, работающая от
имени пользовательского аккаунта, в отличие от чат-бота. Внутренний API,
приватный API, user API, MAX Manager API — недокументированный интерфейс
мессенджера, на котором работают юзерботы.

## Дисклеймер

Проект не является официальным продуктом MAX и не связан с VK. Он опирается на
внутренний (не документированный) API мессенджера, полученный методом обратной
разработки. Из этого следует:

- Использование юзербота **противоречит пользовательскому соглашению MAX** —
  причём сразу по нескольким пунктам, независимо друг от друга. В редакции
  [legal.max.ru/ps](https://legal.max.ru/ps) это 4.3.7 (автоматизированные
  скрипты «для сбора и/или извлечения информации в Сервисе и/или взаимодействия
  с Сервисом и его функциональностью», а также обратная разработка), 4.3.10
  (использование Сервиса «иным способом, кроме как через интерфейс,
  предоставленный Компанией») и 4.4 (интеграция Сервиса со сторонним
  программным обеспечением без отдельного соглашения). Отдельно запрещены спам
  (4.3.4) и массовые однотипные действия ради накрутки счётчиков (4.3.13).
- **Блокировки за сторонние клиенты — не гипотеза.** 1 октября 2025 года
  пресс-служба MAX подтвердила, что Центр безопасности блокирует доступ через
  сторонние приложения; под блокировку попали моды reMAX, Komet, «Зелёный Макс»,
  WhiteMAX. Блокировка применялась к номеру телефона, то есть переживала
  переустановку.
- **Блокируют и за однотипный текст, а не только за объём.** Известны случаи
  бессрочной блокировки за один и тот же ответ, разосланный разным людям вручную.
  Автоматизация, отвечающая всем одинаково, попадает под тот же фильтр — даже
  когда сценарий совершенно законный.
- Внутренний API меняется без предупреждения — работоспособность не
  гарантируется.
- Массовые действия (рассылки, добавление в чаты, сбор данных) с пользовательских
  аккаунтов — прямой путь к блокировке и, в зависимости от сценария, к нарушению
  законодательства о персональных данных.

MAX — не обычный частный сервис: по 156-ФЗ от 24.06.2025 и распоряжению
Правительства № 1880-р он относится к государственной инфраструктуре, и это
упомянуто в самом соглашении. Рамка строже, чем у пользовательского соглашения
рядового мессенджера.

Используйте на свой страх и риск, для личной автоматизации собственных аккаунтов.
