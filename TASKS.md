## Требует живой Windows

Файлы для проверки лежат в
[последнем релизе](https://github.com/stufently/max-messenger-userbot/releases/latest):
`maxub.exe`, `maxubctl.exe` и `build-env.txt` — запись о среде, которая их
собрала.

Собранный `maxub.exe` проверен под Wine: демон стартует, панель отдаётся,
`maxubctl.exe` находит демон, второй запуск не поднимает вторую копию. Под Wine
принципиально не проверяются:

- открытие браузера системной командой;
- окно с ошибкой, реальный `%LOCALAPPDATA%` и его ACL;
- предупреждение SmartScreen: exe не подписан, при первом запуске оно будет;
- **DPAPI**: сам вызов `crypt32.dll`, привязка конверта к учётной записи,
  поведение после смены пароля и при переносе профиля. Проверена только
  политика выбора источника — она от платформы не зависит.

## Требует живого Linux с сеансом

- **Secret Service**: настоящий GNOME Keyring или KWallet, заблокированная
  связка, отсутствие D-Bus под systemd-юнитом. В контейнере хранилища нет
  вовсе, поэтому проверялась только деградация к файлу.
- **Юнит systemd под живым сеансом**: `packaging/linux/maxub.service` принят
  `systemd-analyze verify` (systemd 257), но запуск через `systemctl --user`,
  работу песочницы (`ProtectSystem=strict` вместе с записью в каталог данных) и
  доступность сессионной шины из-под юнита в контейнере не проверить — там нет
  ни systemd как init, ни сеанса пользователя.

## Требует участия человека

Эти шаги нельзя выполнить из кода — нужны доступы и живой аккаунт.

1. **Spike по транспорту** — `PyMax` против `pyromax` на живом аккаунте MAX:
   авторизация по телефону и по QR, reconnect, пагинация истории, медиа,
   edit/delete, пропуски событий, два аккаунта одновременно. Нужен номер
   телефона и готовность к возможной блокировке аккаунта. Решение принимается
   по результату, а не по числу звёзд.
2. **Заполнить настройки GitHub** — description и topics по
   [docs/seo.md](docs/seo.md). Deploy key прав на настройки репозитория не
   имеет, делается вручную в веб-интерфейсе.
3. **Забронировать `max-userbot` на PyPI** — нужен аккаунт PyPI. Имя свободно
   на 2026-07-29.

## Дальше по коду

4. **Проверка адаптера на живом аккаунте** — см. пункт 1: без неё адаптер
   остаётся написанным по исходникам библиотеки, а не по поведению сервера.
5. **Лимиты по чату и адресату, суточные квоты, «прогрев» свежего аккаунта.**
   Механика ключа `(аккаунт, действие)` это уже позволяет, но пороги без данных
   живого сервера будут выдуманными. Ждёт спайка, см. пункт 1.
6. **Образ под arm64** — Raspberry Pi и облачные Graviton/Ampere. Сейчас
   публикуется только amd64. Цена: privileged-контейнер с эмуляцией (binfmt) в
   цепочке сборки, замедление установки под QEMU и сторонний образ, который
   придётся закреплять по digest, — то есть ровно то, чего сейчас в публикации
   нет. Оба ревьюера сошлись на том, что это второй заход, а не первый.

Отложено за пределы v1: планировщик, плагины через `entry_points`, SPA, второй
транспортный адаптер, мост в Telegram (первый внешний плагин после стабилизации
ядра).

Не будет сделано: подмена отпечатка клиента (случайные имя приложения и версия
ОС, как у Heroku) — это обход детектирования, а не личная автоматизация;
обоснование в [docs/research.md](docs/research.md).

## Решено

- **2026-08-01** — транспорт проверяется на настоящем websocket-сервере, и
  `websockets` поднят до 17.0.1. Отставание держалось не на осторожности вообще,
  а на отсутствии проверки: подменная библиотека в тестах означала, что до
  сокета дело не доходит. Теперь есть локальный сервер, говорящий по протоколу
  MAX ровно настолько, чтобы адаптер прошёл handshake, получил событие, отправил
  сообщение и разобрал закрытие. Что именно изменилось — в
  [CHANGELOG.md](CHANGELOG.md). Три вещи проверены в обе стороны: потерянный
  проброс адреса, ответ сервера не тем типом кадра и событие с чужим опкодом
  роняют тест, а не проходят мимо. Отдельный урок записан в гейт CI: тест,
  который умеет пропуститься, обязан предъявить, что он выполнился, — иначе
  исчезнувшая зависимость выглядит как зелёный прогон. Ревьюеры сошлись почти во
  всём; разошлись дважды. Первое: Codex настаивал на проверке ротации токена
  (LOGIN и так формируется, проверка почти бесплатна), Antigravity считал её
  лишней как «логику верхнего уровня pymax» — принят довод Codex, цепочка
  `update_token` → `_refreshed` целиком лежит в библиотеке, и на фейке
  проверялся наш же фейк. Второе: Antigravity нашёл в гейте пропуск проверки
  кода возврата («упавший тест выглядел бы зелёным»), Codex тот же гейт признал
  корректным. Прав оказался Codex — шаг GitHub исполняется как `bash -e`, и
  падение подхватывается само, проверено отдельно. Проверка статуса всё равно
  сделана явной: защита, которой не видно в файле, однажды исчезнет незаметно.
