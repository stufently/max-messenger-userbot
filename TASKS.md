## Ближайшие шаги

Обязательное условие ревью: перечисленное в пунктах 2–5 делается **до**
подключения реального транспорта. Пока транспорт заглушечный, эти пробелы
безопасны; с живым аккаунтом MAX они означают дубли сообщений и потерю событий.

1. **Spike по транспорту** — `PyMax` против `pyromax` на живом аккаунте:
   авторизация, reconnect, пагинация истории, медиа, edit/delete, пропуски
   событий, два аккаунта одновременно. Решение принимается по результату, а не
   по числу звёзд.
2. **Контракт синхронизации** — серверный курсор вместо отметки времени,
   backfill пропущенного за время простоя, супервизор переподключения. Сейчас
   курсор пишется, но пропуски после разрыва не восстанавливаются.
3. **Разбор неоднозначной отправки** — сверка с сервером по клиентскому
   идентификатору. Без серверной идемпотентности гарантия «ровно один раз»
   недостижима, и записи с неизвестным исходом сейчас требуют решения человека.
4. **Расписание повторов, переживающее рестарт** — `next_attempt_at` в БД и
   экспоненциальный backoff. Сейчас лимит попыток есть, а расписание и штрафы
   лимитера теряются при перезапуске.
5. **Шифрование сессий at rest** — ключ вне БД (DPAPI, Secret Service либо
   переданный master key), атомарная ротация. Права 0600 уже выставлены, но
   токен сессии лежит открытым текстом.
6. **Узкие Protocol для зависимостей ядра** — репозиторий и настройки вместо
   конкретных `Storage` и `Settings`, чтобы тестировать восстановление после
   сбоя без реальной БД.
7. **Определить лицензию проекта** — до публикации пакета.
8. **Заполнить настройки GitHub** — description и topics по
   [docs/seo.md](docs/seo.md). Делается вручную в веб-интерфейсе.
9. **Забронировать `max-userbot` на PyPI** — свободно на 2026-07-29.

Отложено за пределы v1: планировщик, плагины через `entry_points`, SPA, второй
транспортный адаптер, мост в Telegram (первый внешний плагин после стабилизации
ядра).
