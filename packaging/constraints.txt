# Закреплённые версии для сборки дистрибутива.
#
# Зачем отдельный файл, а не точные версии в pyproject.toml. Это два разных
# вопроса. В pyproject объявлен контракт библиотеки: «работаю с fastapi от
# 0.115 и новее». Нижние границы там правильные — пользователь, ставящий пакет
# из PyPI рядом с чужими зависимостями, должен иметь свободу выбрать версию, и
# точные пины в метаданных пакета сделали бы его неустанавливаемым в половине
# окружений. Но у сборки дистрибутива требование обратное: собранный сегодня и
# через полгода exe должен состоять из одних и тех же версий, иначе поведение
# релиза невоспроизводимо и баг из отчёта пользователя не повторить. Поэтому
# контракт остаётся в pyproject, а фиксация живёт здесь и подключается только
# там, где собирается артефакт — через `PIP_CONSTRAINT` и `PIP_BUILD_CONSTRAINT`.
#
# Переменные, а не флаг `--constraint`: флаг ограничивает только то, что ставит
# текущий вызов pip, а колесо проекта собирается в отдельном изолированном
# окружении, куда флаг не попадает, — версия hatchling осталась бы плавающей.
# Проверено на pip 25.0.1 и 26.1.2: `PIP_CONSTRAINT` доходит до окружения сборки
# в обоих. `PIP_BUILD_CONSTRAINT` — явная переменная именно для зависимостей
# сборки, она работает в 26.1.2 и молча игнорируется в 25.0.1; задаются обе,
# чтобы закрепление не отвалилось молча, если pip когда-нибудь перестанет
# распространять первую. Путь абсолютный: pip окружения сборки работает из
# своего временного каталога, и относительный путь там не найдётся.
#
# Файл ограничений, а не requirements: он не задаёт, ЧТО ставить (состав
# по-прежнему берётся из pyproject), а только сужает выбор версий. Отсюда же
# следует его слабое место, о котором надо помнить: ограничение на пакет,
# которого здесь нет, отсутствует, и pip об этом не предупредит. Добавили
# зависимость в pyproject — её и её транзитивные пины надо дописать сюда, иначе
# закрепление тихо станет частичным.
#
# Чего эти пины НЕ дают: они фиксируют выбор версии, но не сам файл. Одна и та
# же версия на PyPI теоретически может быть перезалита, и от этого защищает
# только `--require-hashes`. Хеши здесь не заведены сознательно: их пришлось бы
# держать для колёс сразу двух платформ и обновлять при каждой правке, а
# основная задача — убрать зависимость сборки от даты, а не выстроить защиту от
# компрометации индекса.
#
# Как обновлять: поставить `.[dev,pymax]` и pyinstaller без ограничений в чистом
# окружении, прогнать тесты и сборку exe, и перенести сюда вывод `pip freeze`
# (без самого max-userbot). Версии ниже — из фактически работающих окружений:
# Linux/CPython 3.12 (рабочий образ) и Windows/CPython 3.13.14 (сборка exe).
# Придумывать их из головы нельзя: смысл файла в том, что этот набор проверен.
